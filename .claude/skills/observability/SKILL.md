# 관측 (observability)

이 세션의 주제는 운영 상태 측정, 부하 테스트, 성능 분석과 개선이다. 문제를 인지하고, 측정하고, 분석해 결론을 낸다. 결론에 따른 성능 개선을 spec으로 정리해 구현하고, 다시 측정해 성과를 확인한다.

공통 규칙과 코드 작업 규칙은 CLAUDE.md를 따른다. 아래는 이 세션에만 해당하는 내용이다.

## 작업 흐름

1. **문제 인지와 가설:** 무엇이 문제로 보이는지, 어떤 가설을 확인하려는지 사용자와 정리한다.
2. **측정 계획:** 무엇을, 어떤 조건(환경, 데이터 양, 동시 사용자 수, 설정)으로 측정할지 보고하고 승인을 받는다.
3. **측정 준비:** 측정 코드나 수집 구성이 필요하면 spec의 "관측과 성능" 섹션에 먼저 적고, 코드 작업 규칙에 따라 작성한다.
4. **측정:** 측정하고, 원본 숫자와 측정 조건을 보고한다.
5. **분석:** 결과가 무엇을 의미하는지, 가설이 맞았는지를 근거와 함께 분석한다.
6. **결론:** 결론과 개선 방향을 근거와 함께 제시한다. 확정은 사용자가 한다.
7. **개선:** 확정된 개선을 spec으로 정리하고, 코드 작업 규칙에 따라 구현한다. 성능 개선 코드는 면접 소재가 되기 쉬우므로, 누가 어느 부분을 구현할지 반드시 사용자에게 확인한다.
8. **재측정:** 같은 조건으로 다시 측정해 개선 전후를 비교하고 성과를 보고한다.

## 측정 환경

- 운영 상태 관찰은 배포된 운영 서버에서 한다. 로컬 측정은 하지 않는다.
- 부하 테스트는 운영 서버가 아니라, 테스트할 때만 띄우는 별도의 테스트 환경에서 한다. 테스트 환경의 구축과 삭제는 인프라 세션에서 다룬다. 테스트 환경이 운영과 다른 점이 있으면 결과 보고에 함께 밝힌다.
- 실제 사용자 트래픽을 관찰한 결과와, 부하 테스트로 조건을 통제해 얻은 결과를 구분해서 보고한다. 실제 트래픽은 시간대마다 달라서 개선 전후 비교의 근거로는 약하다.

## 부하 테스트 사전 보고

실행 전에 다음을 보고하고 승인을 받는다.

| 항목 | 내용 |
|---|---|
| 대상 | 어느 테스트 환경, 어느 API에 부하를 주는가 |
| 운영과의 차이 | 테스트 환경이 운영 환경과 다른 점 (서버 사양, 데이터 양, 설정) |
| 시나리오 | 동시 사용자 수, 지속 시간, 요청 패턴 |
| 비용 | 테스트 환경을 띄우는 시간과 트래픽, 오토스케일링으로 발생할 수 있는 비용 |
| 데이터 | 테스트에 쓸 데이터를 어떻게 준비하는가 |
| 중단 기준 | 에러율이나 응답 시간이 어느 수준을 넘으면 즉시 중단하는가 |
| 외부 요인 | Cloudflare 같은 중간 계층이 테스트 트래픽을 차단하거나 결과에 영향을 주는지 |

## 측정값 보고

측정 결과는 이 세션 안에서 원본 그대로 보여준다. 사용자가 이해하고, 나중에 records에 옮겨 정리할 때 쓴다.

- 요약하거나 반올림하지 말고 원본을 보여준다.
- 측정 조건을 함께 적는다. 조건이 없는 숫자는 비교할 수 없다.
- 개선 전후를 비교할 때는 같은 조건에서 측정한다. 조건이 달라졌다면 무엇이 달라졌는지 밝힌다.
- 숫자가 무엇을 의미하는지, 어떻게 읽는지 함께 설명한다.
- 가설과 결론을 구분해서 말한다. 근거 없이 결론을 내리지 않는다.

## 멈출 조건 (관측)

공통 멈출 조건에 더해, 다음 상황에서도 멈추고 사용자에게 보고한다.

1. 부하 테스트를 실행하기 전 (위 "부하 테스트 사전 보고"와 함께)
2. 모니터링 도구나 부하 테스트 구성 요소를 새로 정해야 할 때. 구성 요소 선택은 PM 세션에서 다룬다
3. 결론이 아키텍처 변경을 요구할 때. 상황과 문제를 이 세션에서 보고한다. 사용자가 이해한 뒤 PM 세션에서 결정한다
4. 개선 전후의 측정 조건을 같게 맞출 수 없을 때

## 다루지 않는 것

- 모니터링 도구를 서버에 배포하고 연결하는 일, 테스트 환경을 띄우고 지우는 일은 인프라 세션에서 다룬다.
- 성능과 무관한 기능 구현은 백엔드 세션에서 다룬다.
