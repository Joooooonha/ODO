## 1. 문제 정의와 목표 설정

### 1.1 서비스 요구를 기술 문제로 번역

서비스가 사용자에게 약속하는 것은 한 문장입니다.

> "프로 댄서 영상과 비교해서, 어디가 어떻게 다른지 알려준다."

이를 기술 문제로 바꾸면 **"두 영상에서 같은 동작에 해당하는 지점을 찾고, 그 지점에서
자세가 얼마나 다른지 수치화한다"** 가 됩니다. 여기에는 서로 독립적인 요구가 섞여
있어서, 하나로 뭉뚱그리면 어디가 잘못됐는지 진단할 수 없습니다.

### 1.2 세 축으로의 분해

| 축 | 질문 | 실패 시 증상 |
|---|---|---|
| **① 탐지** | 관절 좌표가 올바르게 추출되는가 | 비교 대상 데이터 자체가 오염 |
| **② 정렬** | 서로 다른 시간대의 같은 동작이 매핑되는가 | 다른 동작끼리 비교 |
| **③ 표현** | 촬영 조건 차이가 동작 차이로 오인되지 않는가 | ①②가 완벽해도 최종 수치가 무의미 |

**③은 처음부터 있던 축이 아닙니다.** 초기 문제 정의는 ①②뿐이었습니다. 그런데
"관절을 정확히 잡고 시점도 정확히 맞췄는데, 두 영상의 카메라 거리·위치가 다르면
좌표값 자체가 다르게 나오지 않는가"라는 질문에서 출발해, 실제로 측정해보니
**좌표 기반 비교가 동작 차이가 아니라 프레이밍 차이를 재고 있었다**는 것이
확인되어 별도 축으로 승격했습니다 ([5.2](#52-비교-표현--좌표에서-관절-각도로)).

이 분해가 이후 모든 작업의 뼈대가 됩니다. 각 축은 **검증 방법이 다르고, 병목이
다르고, 해결 수단이 다릅니다.**

### 1.3 성공 기준을 어떻게 정의했는가

"정확도가 높다"는 기준이 될 수 없습니다. 무엇에 대한 정확도인지가 축마다 다르기
때문입니다. 그래서 측정 층위를 둘로 나눴습니다.

| 층위 | 재는 것 | 단위 | 정답(GT) |
|---|---|---|---|
| **L1. 포즈 추정 정확도** | 관절 좌표가 정답에 얼마나 가까운가 | mAP, PCK | 사람이 찍은 키포인트 |
| **L2. 동작 비교 품질** | 정렬이 맞게 됐는가 | 초(정렬 오차) | 대응 시점 정답 |

**핵심 판단**: 축 ①은 L1으로, 축 ②③은 L2로 검증한다. 그리고 **L2를 먼저 구축한다.**
이유는 [4장](#4-검증-체계-설계--가장-먼저-한-일)에서 설명합니다.

## 2. 전제와 가정

측정 결과를 해석하려면 어떤 조건에서 얻은 값인지가 명확해야 합니다. 아래는 현재
구현이 **암묵적으로 또는 명시적으로 기대하는 조건**과, 그 조건이 깨졌을 때
무슨 일이 일어나는지입니다.

| # | 가정 | 왜 필요한가 | 깨지면 |
|---|---|---|---|
| A1 | **프레임에 댄서가 한 명** | 다중 인물 중 대상을 고르는 로직이 없어 검출 결과의 첫 번째를 사용 | 배경 인물이 잡히면 엉뚱한 사람을 분석. 실서비스 전환 시 "중앙 + 최대 움직임" 휴리스틱 + IoU 추적 필요 |
| A2 | **두 영상이 같은 안무** | 몸통 회전을 보정하지 않는 근거. 같은 안무면 두 영상이 같은 시점에 같은 방향으로 회전해 왜곡이 상쇄됨 | 회전 차이가 동작 오차로 계산됨 |
| A3 | **대체로 정면 촬영** | 2D 투영에서 관절 각도가 실제 각도를 근사 | 측면일수록 self-occlusion과 투영 단축(foreshortening)이 심해져 각도가 왜곡. 정면성 지표로 감지는 하되 보정은 안 함 |
| A4 | **몸통 4점(양 어깨·양 엉덩이)이 보임** | 몸통 상대 각도·정면성·카메라 롤 보정이 전부 몸통 축에 의존 | 계산 자체가 불가능. 신뢰도 문제가 아니라 가능/불가능 문제라 별도 게이트로 분리 |
| A5 | **촬영 중 카메라가 고정** | 영상 전체의 몸통 축 중앙값을 "수직"으로 삼는 자가 보정이 성립하려면 카메라 기울기가 영상 내내 상수여야 함 | 중간에 팬/틸트가 일어나면 보정 기준이 흔들림. **현재 감지 로직 없음** |
| A6 | **고정 프레임레이트(CFR)** | 프레임 인덱스를 fps로 나눠 초로 환산 | 가변 프레임레이트(VFR) 영상에서 시간 계산이 어긋남. **현재 미고려** |
| A7 | **배치 처리 (실시간 불필요)** | 무거운 모델·프레임 서브샘플링 등 지연을 감수하는 선택의 전제 | 실시간 요구가 생기면 모델 선택이 전면 재검토 대상 |
| A8 | **2D 포즈로 충분** | 3D 추정을 도입하지 않은 근거 | 회전·단축 문제의 근본 해결은 3D가 필요. 현재는 보류(재검토 조건은 [8장](#8-현재-한계와-미검증-영역)) |

> A5, A6은 작업 중 **명시되지 않은 채 전제되고 있던 것**을 문서화 단계에서 발견해
> 추가한 항목입니다. 현재 코드에 감지·대응 로직이 없습니다.

## 4. 검증 체계 설계 — 가장 먼저 한 일

### 4.1 왜 기능이 아니라 검증부터였는가

작업 착수 시점의 상태는 이랬습니다.

- 파이프라인은 동작하고 점수도 출력된다
- 그러나 **그 점수가 타당한지 확인할 방법이 전혀 없다**

이 상태에서 코드를 고치면 고쳤는지조차 알 수 없습니다. "정렬이 잘 됐다"고 말하려면
"원래 어디에 정렬됐어야 하는가"라는 정답이 필요한데, 그것이 없었습니다.

그래서 **첫 작업을 정답 확보로 잡았습니다.** 결과적으로 이 판단이 이후 발견한
버그 3개를 전부 정량적으로 확인·수정할 수 있게 한 근거가 됩니다.

### 4.2 정답을 만드는 두 가지 경로

| 방식 | 밀도 | 현실성 | 비용 |
|---|---|---|---|
| **사람이 대응 시점을 라벨링(앵커)** | sparse (10~15점) | 높음 | 사람 시간 |
| **정답을 아는 데이터를 합성** | **dense (전 프레임)** | 낮음 | 없음 |

두 방식은 **경쟁이 아니라 보완 관계**입니다.

- 합성 GT는 **정밀 측정** 담당 — 변형이 결정적이므로 "변형본 프레임 i는 원본 몇 번
  프레임에서 왔는지"를 모든 프레임에 대해 정확히 압니다.
- 앵커는 **현실성 검증** 담당 — 실제 두 사람 사이에서도 통하는지는 이것으로만
  확인 가능합니다.

먼저 확보 가능한 합성 GT로 시작하고, 앵커는 사용자 작업으로 병행했습니다.

### 4.3 합성 GT의 설계

원본 영상에서 시간축 또는 공간을 **결정적으로** 변형한 사본을 만들고, 프레임 인덱스
매핑을 정답으로 저장합니다. ffmpeg 없이 OpenCV로 프레임을 직접 재배열하는데,
**프레임 단위 인덱스 매핑이 곧 정답**이라 애매함이 없기 때문입니다.

| 변형 | 시뮬레이션 상황 | 검증 대상 |
|---|---|---|
| `offset` | 녹화를 늦게 시작 | 전역 시간 오프셋 복원 |
| `speed 0.9 / 1.1` | 전체적으로 느리게/빠르게 춤 | 전역 속도 차이 흡수 |
| `local` | 중간 한 구간만 느려짐 | **구간별 워핑** — DTW가 진짜 필요한 케이스 |
| `trim` | 안무의 일부만 춤 | 끝점이 대응되지 않는 경우 |
| `zoom / shift / roll` | 카메라 거리·위치·기울기 차이 | **시간축은 항등** → feature의 촬영조건 불변성 |
| `reencode` | 변형 없이 재인코딩만 | **대조군** |

**대조군(`reencode`) 설계가 이 체계의 핵심입니다.** 다른 변형에서 오차가 나왔을 때
그것이 "변형 때문"인지 "포즈 추정이 원래 그만큼 흔들려서"인지 구분하려면 노이즈
바닥을 알아야 합니다. 대조군 없이는 모든 측정이 해석 불가능한 숫자에 그칩니다.

**공간 변형의 설계 의도**: 시간축을 항등으로 두면(프레임 i ↔ 프레임 i) 정렬 문제가
사라지고, 프레임 i를 i와 직접 비교했을 때 남는 오차는 **전부 feature가 촬영 조건
차이를 걸러내지 못한 양**이 됩니다. 축 ③만 분리해서 재기 위한 장치입니다.

### 4.4 이 체계의 구조적 한계 (설계 시점에 인지)

변형본은 원본과 같은 영상에서 나오므로 두 포즈 시퀀스가 거의 동일합니다. 따라서
합성 GT가 증명할 수 있는 것과 없는 것이 명확히 갈립니다.

- ✅ **증명 가능**: 정렬 기계가 의도대로 작동하는가 (**정확성** 검증)
- ❌ **증명 불가**: 다른 댄서 사이에서도 정렬되는가 (**난이도** 검증)

이 한계를 알고 시작했고, 그래서 앵커 확보를 병행 과제로 뒀습니다.

## 5. 기술 선택 과정

각 항목은 **배경 → 후보 → 판단 근거 → 결정 → 검증** 순으로 정리했습니다.

### 5.1 시간축 정렬 — DTW 구현 교체

**배경**

기존 코드는 `dtaidistance.dtw.distance()`를 사용하고 있었습니다. 4.3의 dense GT로
측정하자 **2초(60프레임) 앞부분이 잘린 영상에서 정렬 오차 중앙값이 정확히 2.000초**로
나왔습니다.

오차가 오프셋 값과 정확히 일치한다는 것은 랜덤한 부정확이 아니라 **시간 어긋남을
전혀 감지하지 못하고 프레임 i를 i에 그대로 매칭**하고 있다는 신호였습니다.

**원인**

`dtw.distance()`는 **1차원 스칼라 시계열 전용** API입니다. 여기에 `(프레임수 × 51,)`로
통짜 flatten한 다차원 데이터를 넣고 있었습니다. 그러면 프레임 경계가 사라져
"5번 프레임의 y좌표"와 "6번 프레임의 x좌표"를 정렬하는 꼴이 됩니다. `window=7`도
"7프레임 허용"이 아니라 "숫자 7개 허용"(≈0.14프레임)으로 해석되어 사실상 정렬 여유가
없었습니다.

**후보 검토**

| 후보 | 판단 |
|---|---|
| `fastdtw` | ❌ 근사 알고리즘이라 최적 경로를 보장하지 않고, 실무 데이터 크기에서 밴드 제약 정확 DTW보다 오히려 느림 (Wu & Keogh, IEEE TKDE) |
| `dtaidistance.dtw_ndim` | ✅ **다변량 지원**. 프레임 하나를 하나의 점으로 취급. 기존 의존성 유지 |
| `tslearn` | 다변량 지원하나 새 의존성 필요 → 보류 |

**결정**: `dtw_ndim`. 라이브러리 교체가 아니라 **같은 라이브러리의 올바른 API로 전환**.

**검증** (동일 dense GT, offset 변형)

| 구현 | 대응된 프레임 | 중앙 오차 | ±2프레임 내 | 소요 |
|---|---|---|---|---|
| 기존 (1D flatten) | 203/333 (61%) | 2.000초 | 0.0% | 60.4초 |
| **개선 (`dtw_ndim`)** | **333/333 (100%)** | **0.000초** | **97.6%** | **0.07초** |

**추가 구현 — 밴드 제약 가드**

`window`가 두 시퀀스의 길이 차이보다 작으면 경로를 만들 수 없습니다. `align()`에서
`window = max(요청값, |길이차| + 1)`로 자동 확장하도록 했고, 그 덕분에 60프레임
오프셋도 `window=15` 설정에서 복원됩니다. window를 15~150 및 제약 없음으로 스윕해도
결과가 동일했습니다.

### 5.2 비교 표현 — 좌표에서 관절 각도로

**배경**

축 ③의 존재를 확인하기 위해 공간 변형본으로 측정했습니다. 시간축이 항등이므로
프레임 i를 i와 직접 비교하면 남는 오차는 전부 촬영 조건에서 온 것입니다.

**측정 결과**

| 변형 | 좌표 기반 중앙 오차 | 대조군 대비 | 각도 기반 중앙 오차 | 대조군 대비 |
|---|---|---|---|---|
| 재인코딩만 (대조군) | 0.00082 | 1x | 0.65° | 1x |
| 줌 1.3배 | 0.0391 | **47.5x** | 3.54° | 5.4x |
| 위치 이동 | 0.1047 | **127.3x** | 3.15° | 4.8x |
| 카메라 8° 기울임 | 0.0184 | **22.4x** | 3.30° | 5.1x |

**결과의 의미**

1. **좌표 오차는 변형의 크기 그 자체입니다.** 위치 이동에 적용한 변위를 높이 단위로
   환산하면 `√((0.12 × 1080/1920)² + 0.08²) = 0.1047`인데, 측정된 좌표 오차도
   **0.1047로 소수점 넷째 자리까지 일치**했습니다. 좌표 feature가 동작 차이가 아니라
   프레이밍 차이를 그대로 재고 있었다는 직접적 증거입니다.

2. **각도 오차는 변형 종류와 무관하게 일정**(3.15~3.54°)합니다. 좌표 영향이 5.7배
   차이 나는(0.0184 vs 0.1047) 세 변형에서 각도가 거의 같다는 것은, 남은 오차가
   변형 때문이 아니라 포즈 추정 흔들림임을 뜻합니다.

**왜 각도인가 — 원리**

각도는 정의상 **이동(translation)과 균등 스케일(scale)에 불변**입니다. 따라서 카메라
거리·화면 내 위치 차이를 보정하는 정규화가 **원리적으로 불필요해집니다.** 좌표
정규화를 "잘 하는 법"을 고민하는 대신, 정규화가 필요 없는 표현으로 바꾼 것입니다.

**bbox 기준 정규화를 택하지 않은 이유**: bbox 크기는 팔을 벌리면 커지고 오므리면
작아져 **측정 대상(자세)에 종속적**입니다. 정규화 기준이 자세에 따라 요동치면
순환 오염이 발생합니다. 몸통 축은 팔다리 동작과 무관하게 안정적입니다.

**feature 설계 (총 14종)**

| 분류 | 개수 | 항목 | 기준 |
|---|---|---|---|
| 분절 방향각 | 8 | 상완·전완·허벅지·정강이 (좌/우) | **몸통 축 상대** |
| 몸통 기울기 | 1 | 어깨중점→엉덩이중점 | 절대(자가 보정) |
| 목 | 1 | 어깨중점→코 | 몸통 상대 |
| 굽힘각 | 4 | 팔꿈치·무릎 (좌/우) | 3점 내각 |

굽힘각은 정보량 면에서 분절 방향각으로부터 유도 가능하지만, **사용자 피드백 문구**를
위해 별도로 계산합니다("오른쪽 팔꿈치가 기준보다 덜 굽혀졌습니다").

**카메라 롤 대응 — 자가 보정**

팔·다리를 몸통 축 상대로 재면 카메라 기울기가 자동 상쇄됩니다(몸통과 팔이 같이
회전하므로 상대 각도는 불변). 그러나 몸통 기울기 자체는 절대 기준이 필요합니다.

여기서 촬영 가이드("폰을 수평으로")는 현실적이지 않다고 판단해, **영상별 몸통 축
각도의 중앙값을 그 영상의 "수직"으로 정의**하는 방식을 택했습니다.

- 근거: 카메라 롤은 몸통 축 분포 전체를 **일정하게 shift시키는 상수 오프셋**이므로
  중앙값을 빼면 상쇄됩니다.
- 목적이 "절대 수직 복원"이 아니라 **"두 영상의 기준을 서로 맞추는 것"** 이라
  바닥 동작이 많아 중앙값이 실제 수직이 아니어도 무방합니다.
- 검증: 카메라를 8° 돌린 영상에서 몸통 기울기 오차가 **1.0°에 그쳤습니다**
  (보정이 없었다면 8°가 그대로 나와야 함).
- 실제 데이터에서도 작동: `real` 쌍에서 사용자 +2.2°, 기준 +0.9°의 롤 차이를 검출·보정.

**각도의 순환성 처리**

각도는 순환량이라 −179°와 +179°는 2° 차이지 358° 차이가 아닙니다. 원값을 그대로
Euclidean 거리에 넣으면 경계에서 튑니다. 그래서 DTW 입력은 `(cos θ, sin θ)`로
인코딩하고, 오차는 `atan2(sin Δ, cos Δ)` 기반 순환 차이로 계산합니다.

**몸통 회전(yaw/pitch)은 보정하지 않기로 한 이유**

가정 A2(같은 안무)에 따라, 두 영상은 같은 시점에 같은 방향으로 회전합니다. 즉
왜곡이 양쪽에 공통으로 걸려 상당 부분 상쇄됩니다. **회전 자체는 안무의 일부지
오차가 아닙니다.** 대신 `어깨너비 / 몸통길이` 비율을 **정면성 지표**로 계산해
2D 각도를 얼마나 신뢰할 수 있는지의 참고값으로 기록합니다.

정면성은 기본적으로 게이트하지 않고 통계만 남깁니다 — **적절한 임계값이 아직
검증되지 않았기 때문**입니다. `--min-frontality`로 켤 수 있게만 열어뒀습니다.

### 5.3 결측 관절 처리 — 0 채움에서 명시적 마스크로

**발견한 문제**

기존 구현은 가려지거나 검출되지 않은 관절을 `0`으로 채웠습니다. 그런데 두 영상 모두
해당 관절이 `0`이면 거리도 `0`이 되어 **"완벽하게 일치"로 계산**됩니다.
즉 **가려질수록 점수가 오르는 역전**이 발생하고 있었습니다. 검출이 통째로 실패한
프레임은 전 관절이 0이 되므로 영향이 더 큽니다.

**설계 원칙**

> 보이지 않는 관절을 추측해서 "잘했다/못했다"를 판정하는 것은 둘 다 부정직하다.
> 정면 관객 시점에서 보이지 않는 것은 평가에서 제외한다.

**구현**

| 항목 | 방식 |
|---|---|
| 표현 | 좌표와 **별도의 유효성 불리언 마스크**를 함께 보관 (NaN 대신 명시적 마스크 — DTW 라이브러리가 NaN을 조용히 이상하게 처리할 위험 회피) |
| 거리 계산 | **양쪽 모두 유효한 항목만** 사용(pairwise 판정) 후 **유효 개수로 평균** |
| 프레임 게이트 | **2단 구조** (아래) |

**2단 프레임 게이트를 나눈 이유**

- **(a) 몸통 4점 필수** — 없으면 몸통 상대 각도·정면성·롤 보정이 **계산 자체가 불가능**합니다. 이는 "얼마나 신뢰할 수 있나"가 아니라 "계산이 되나 안 되나"의 문제라 비율 임계와 성격이 다릅니다.
- **(b) 유효 feature 비율 임계** (기본 30%) — 낮게 잡았습니다. 유효 항목만 평균내는 구조라 항목이 적어도 그 값 자체는 정직하기 때문입니다.

게이트에 걸린 프레임은 버리지 않고 **"평가 불가"로 집계해 결과에 기록**합니다.
사용자에게는 재촬영 근거가 되고, 모델 비교에서는 품질 지표가 됩니다.

**정렬용 / 채점용 feature 분리**

두 용도의 요구가 상충합니다.

| 용도 | 요구 | 처리 |
|---|---|---|
| **정렬(DTW 입력)** | 연속성 — 값이 비면 워핑 경로가 망가짐 | 짧은 구간 보간 |
| **채점(거리 계산)** | 정직성 — 없는 값을 지어내면 안 됨 | 마스킹 엄격 적용 |

**이 분리가 성립하는 근거**: DTW는 "어디와 어디가 대응하는지"(path)만 결정하고
값 자체는 최종 점수에 쓰이지 않습니다. 따라서 정렬용에 들어간 보간값이 채점을
오염시키지 않습니다.

보간 범위는 **5프레임(≈0.17초) 이하 구간만**으로 제한했습니다. 긴 구간 보간은 없는
데이터를 만들어내는 것이고, 겹침 중에 실제로 빠른 동작이 있었다면 그것을 매끄럽게
덮어버리기 때문입니다. 긴 구간은 직전 값을 유지해 연속성만 확보합니다.

### 5.4 부분 안무 대응 — psi 끝점 완화

**배경**

일반 DTW는 경로가 (0,0)에서 시작해 (n−1, m−1)에서 끝나도록 **강제**합니다. 두
영상이 처음부터 끝까지 대응한다는 가정인데, 실서비스에서는 사용자가 안무의 일부만
추거나 앞뒤에 여백이 들어가는 것이 훨씬 흔합니다.

**해결**: dtaidistance의 psi 완화 — 양 끝에서 최대 psi프레임까지 대응 없이 건너뛸
수 있게 합니다.

**검증** (`trim` 변형 = 원본의 25%~70% 구간만, 앞 98프레임·뒤 118프레임이 미대응)

| psi | 평균 오차 | 최대 오차 | ±5프레임 내 |
|---|---|---|---|
| 없음(끝점 강제) | 0.446초 | 3.733초 | 83.1% |
| 30 | 0.323초 | 2.333초 | 83.5% |
| 60 | 0.208초 | 1.433초 | 83.5% |
| **100** | **0.002초** | 0.317초 | **99.4%** |
| 130 | 0.000초 | 0.017초 | 100% |

**psi가 잘려나간 앞부분(98프레임) 이상이 되는 지점에서 정확히 정렬이 붙습니다.**
우연이 아니라 원리대로 동작한다는 확인입니다.

**기본값으로 켠 근거** — 전체가 정상 대응하는 경우에도 손해가 없음을 확인:

| 변형 | psi 없음 | psi=100 | 판정 |
|---|---|---|---|
| trim | 0.446초 (83.1%) | **0.002초 (99.4%)** | 대폭 개선 |
| offset | 0.074초 (96.4%) | **0.001초 (100%)** | 개선 |
| speed 0.90 | 0.002초 | 0.002초 | 동일 |
| local 0.50 | 0.003초 | 0.003초 | 동일 |

손해 0건, 이득 2건 → **기본 활성화**. 인자는 프레임이 아니라 **초 단위**(`--psi-sec`,
기본 3.0)로 받습니다. 영상마다 fps가 달라 프레임 수로 고정하면 안 되기 때문입니다.

**구현 함정**: psi가 짧은 쪽 시퀀스 길이를 넘으면 dtaidistance가 `IndexError`로
죽습니다. `align()`에서 상한을 잘라냅니다.

### 5.5 포즈 추정 모델 선정

**제약**: L1 GT가 없어 "어느 모델이 정확한가"의 **순위를 매길 수 없습니다.**
그래서 **라벨 없이 잴 수 있는 품질의 필요조건**을 설계했습니다.

| 지표 | 원리 | 무엇을 잡아내는가 |
|---|---|---|
| **뼈 길이 안정성** | 사람 몸은 강체 → 프레임 간 뼈 길이 급변은 동작이 아니라 추정 오류 | **겹침 구간에서 모델이 가려진 관절을 지어내면 여기서 잡힘** = 라벨 없는 겹침 오류 탐지기 |
| 시간적 흔들림 | 같은 영상이면 실제 움직임이 동일 → 차이는 모델 흔들림 | 프레임 간 불안정성 |
| 모델 간 불일치 | 정답을 몰라도 "여기가 어렵다"는 알 수 있음 | **L1 라벨링 대상 프레임 선정** |
| 비용 | fps / 지연 | 배포 가능성 |

투영 단축은 부드럽게 변하므로 **프레임 간 급변만** 보면 단축과 오류가 구분됩니다.
모든 지표는 몸통 길이로 정규화해 카메라 거리에 무관하게 만들었습니다.

**측정 방법론상의 함정 2건 (실험 중 발견)**

1. **모델 간 "유효율"은 비교하면 안 됩니다.** 신뢰도 캘리브레이션이 모델마다 다릅니다.
   실측에서 yolov8x가 yolov8n보다 유효율이 **낮게** 나왔는데(91.8% vs 93.3%), 이는
   큰 모델이 나쁜 게 아니라 **과신하지 않는다**는 뜻일 수 있습니다.
   → 품질 지표는 낮은 임계값(0.1)으로 계산합니다. 걸러낸 뒤가 아니라 **걸러내기 전의
   기하학적 일관성**을 봐야 모델끼리 공정합니다.
2. **`memory_MB` 열은 신뢰 불가.** `tracemalloc`은 파이썬 수준 할당만 추적해
   torch/ONNX가 C++에서 잡는 메모리가 빠집니다. yolov8n 78MB, yolov8x 14MB로 역전되어
   나옵니다. 비교하려면 RSS를 별도 측정해야 합니다.

**결과** (`real/user_dancer.mp4` 393프레임)

| 모델 | 뼈 불안정 ↓ | 흔들림 ↓ | fps | 지연 ms | 장치 |
|---|---|---|---|---|---|
| yolov8n-pose (기존) | 0.0143 | 0.0381 | 26.0 | 38.4 | MPS |
| **yolo11x-pose** | **0.0127** | **0.0363** | 5.7 | 176.7 | MPS |
| MediaPipe Full | 0.0189 | 0.0372 | 29.1 | 34.4 | — |
| ViTPose-base-simple | 0.0136 | 0.0367 | 6.0 | 167.8 | MPS |
| RTMPose-l (384×288) | 0.0150 | 0.0389 | 3.6 | 274.9 | **CPU** |

**결정**: `yolo11x-pose`. 다만 아래 단서를 반드시 함께 읽어야 합니다.

**해석 시 필수 단서 4개**

1. **RTMPose만 CPU에서 실행**되었습니다(onnxruntime). 속도 비교는 RTMPose에 불리합니다. 품질 지표는 장치와 무관하므로 유효합니다.
2. **모델 크기가 맞춰지지 않았습니다.** ViTPose는 base(large 아님), RTMPose는 l(x 아님)입니다. "ViTPose/RTMPose가 나쁘다"로 일반화할 수 없습니다.
3. **정확도의 대리 지표지 정확도가 아닙니다.** 뼈 길이가 안정적이어도 일관되게 틀린 위치를 찍을 수 있습니다.
4. **테스트 영상이 쉽습니다.** 5개 모델 모두 검출 실패 0프레임입니다. 정작 중요한 겹침 구간이 스트레스되지 않았으므로 **겹침이 많은 영상에서는 순위가 바뀔 수 있습니다.**

**모델 간 불일치의 활용**

| 쌍 | 불일치 |
|---|---|
| yolov8x ↔ yolo11x (같은 계열) | 0.0326 |
| MediaPipe 1 ↔ 2 (같은 계열) | 0.0342 |
| **yolo11x ↔ ViTPose (계열 다름, 둘 다 상위)** | **0.0388** |
| YOLO 계열 ↔ MediaPipe 계열 | 0.0565~0.0733 |

두 가지를 읽을 수 있습니다.

- **뼈 안정성 상위 두 모델이 서로 가장 근접**(0.0388)합니다. 계열이 달라도 계열 내부
  수준으로 일치한다는 것은 둘 다 같은 지점으로 수렴한다는 뜻으로 읽을 수 있습니다.
  라벨 없이 얻는 간접적 정확도 신호입니다. **다만 추론이지 증명이 아닙니다.**
- **계열 간(0.057~0.073)이 계열 내부(0.033)의 2배**입니다. 계열 간 차이에는
  "어려운 프레임"뿐 아니라 관절 정의의 체계적 차이(COCO17 vs BlazePose의 어깨·엉덩이
  위치 규약)가 섞여 있습니다. → **L1 라벨링 대상 프레임은 같은 계열 두 모델의
  불일치로 고르는 편이 깨끗합니다.** 체계적 오프셋이 상쇄되어 진짜 어려운 프레임만
  남습니다.

**hybrid 방식 폐기**

YOLO로 사람을 검출한 뒤 그 영역만 MediaPipe로 처리하는 2단계 방식이 이론과 반대로
더 나빴습니다.

| 백엔드 | 기준영상 유효율 | 사용자영상 유효율 | 평가불가 프레임 |
|---|---|---|---|
| yolo | 95.5% | 93.3% | 0.0% |
| mediapipe (전체 프레임) | 97.2% | 97.8% | 0.3% |
| hybrid (YOLO crop → MediaPipe) | **83.5%** | 94.5% | **8.7%** |

hybrid는 MediaPipe와 **같은 포즈 모델을 쓰는데도** 유효율이 13.7%p 낮습니다. 차이는
입력이 전체 프레임이냐 잘라낸 영역이냐뿐이므로 **crop 단계**로 원인이 좁혀집니다.

흥미로운 후속 확인: 나중에 도입한 ViTPose·RTMPose도 **같은 2단계 방식**인데 문제가
없었습니다. 이들은 라이브러리가 **종횡비를 지키며 패딩·아핀 변환**으로 정규화하고
출력을 원본 좌표계로 되돌립니다. 반면 hybrid는 배열을 직접 잘라
(`frame[y1:y2, x1:x2]`) 종횡비가 깨지고 경계에서 신체가 잘렸습니다.

→ **2단계 방식이 문제가 아니라 crop 구현이 문제였습니다.** 코드는 삭제하지 않고
폐기 표시만 남겨 실험 기록으로 보존했습니다.

### 5.6 프레임 서브샘플링

**동기**: 배포 비용에 직결됩니다. 30fps를 전부 추론할 필요가 없다면 연산이 k배
줄어들고, 이는 "무거운 모델을 쓸 수 있느냐"를 가릅니다.

**측정 설계**: 포즈 추정을 다시 돌리지 않고 캐시된 시퀀스에서 k번째 프레임만
골라냅니다. 실제로 k배 띄엄띄엄 추론한 것과 같은 입력입니다.

**정렬(L2)에 대한 영향** — `local` 변형(시간적으로 가장 어려운 케이스)

| 배수 | 유효 fps | 연산량 | 평균 오차 | 해상도 하한 | ±5프레임 내 |
|---|---|---|---|---|---|
| ×1 | 30.0 | 100% | 0.003초 | 0.017초 | 100% |
| ×2 | 15.0 | 50% | 0.007초 | 0.033초 | 100% |
| ×3 | 10.0 | 33% | 0.030초 | 0.050초 | 100% |
| ×6 | 5.0 | 17% | 0.049초 | 0.100초 | 100% |

**오차가 해상도 하한(k/2 프레임)을 따라갑니다.** 즉 저하의 대부분이 알고리즘 붕괴가
아니라 **시간 해상도의 원리적 한계**입니다.

**이것이 모델 선택을 바꿉니다**

| 구성 | 원본 프레임당 실효 비용 | 뼈 불안정 |
|---|---|---|
| yolov8n @ 30fps | 38.4ms | 0.0143 |
| **yolo11x @ 10fps** | **58.9ms** | **0.0127** |
| yolo11x @ 30fps | 176.7ms | 0.0127 |

"무거운 모델은 비싸서 못 쓴다"는 전제가 서브샘플링과 결합하면 성립하지 않습니다.

**채점에 대한 영향 — 결론이 다릅니다**

정렬이 멀쩡해도 프레임을 건너뛰면 빠른 동작의 순간 오차를 놓칠 수 있습니다.
별도 측정했습니다.

| 배수 | 점수 | 평균 | p90 | 최대 | 채점쌍 |
|---|---|---|---|---|---|
| ×1 | 46.4 | 24.11° | 42.18 | 104.62 | 455 |
| ×3 | 46.6 | 24.02 | 37.87 | 90.01 | 134 |
| ×6 | **54.0** | 20.72 | 32.69 | 47.27 | 47 |

프레임을 덜 봤다는 이유만으로 점수가 올라갑니다(46.4 → 54.0).

**여기서 교란 변수를 통제해야 했습니다.** 채점쌍 수도 455 → 47로 줄어드는데,
표본이 작아지면 최대값은 그것만으로도 낮아집니다. 그래서 **k=1의 오차 분포에서 같은
개수만 무작위 추출(1000회)** 하는 대조군을 만들어 분리했습니다.

| 배수 | n | p90 실제 vs 대조 | 최대 실제 vs 대조 |
|---|---|---|---|
| ×2 | 212 | 37.83 vs 41.99±1.49 (**−2.8σ**) | 86.60 vs 93.06±13.77 (−0.5σ) |
| ×4 | 104 | 35.99 vs 41.93±2.55 (**−2.3σ**) | 62.84 vs 80.28±16.85 (−1.0σ) |
| ×6 | 47 | 32.69 vs 41.49±4.55 (**−1.9σ**) | 47.27 vs 69.03±17.74 (−1.2σ) |

- 처음 눈에 띈 "최대 오차 −54.8%"는 **대부분 표본 축소 효과**였습니다(대조군 편차
  ±14~18에 묻힘). 최대값은 표본 크기에 지나치게 민감해 이 목적의 지표로 부적절합니다.
- 반면 **p90은 모든 배수에서 일관되게 약 −2σ**로, 표본 크기로 설명되지 않는
  **실제 정보 손실**입니다(10~22% 과소평가).

**설계 권고**: 정렬과 채점의 요구가 다르므로 분리합니다.
- 정렬은 서브샘플링에 강건 → 띄엄띄엄 처리 가능
- 채점은 정보 손실이 있으므로 전체 프레임 권장
- **최선: 서브샘플로 정렬 경로를 구하고, 그 경로를 보간해 전체 프레임에서 채점**
  (무거운 포즈 추정은 정렬용으로만, 채점은 촘촘하게) — **현재 미구현**

### 5.7 오디오 사전 정렬

**착안**: 춤은 음악에 맞춰 춥니다. 같은 곡이면 **오디오만으로 전역 시간 오프셋을
확정**할 수 있고, 그러면 DTW는 미세 타이밍만 다루면 되므로 탐색 공간이 줄고 정렬
실패 가능성도 낮아집니다.

**원파형이 아니라 온셋 포락선을 쓴 이유**: 두 영상은 따로 촬영되어 마이크·거리·잔향이
다르므로 파형 자체는 잘 맞지 않습니다. 반면 "소리가 커지는 순간"(에너지의 양의 변화)은
녹음 조건이 달라도 같은 시점에 나타납니다.

**정답을 아는 케이스 검증**

| 정답 오프셋 | 추정값 | 오차 |
|---|---|---|
| 2.000초 | 1.997초 | 3ms |
| 0.700초 | 0.697초 | 3ms |

3ms는 포락선 해상도(86fps → 11.6ms) 안쪽입니다.

**음성 대조군에서 판별기가 처음엔 실패했습니다.** 서로 다른 영상끼리도 신뢰도
9~10이 나와 임계 3.0을 통과했습니다.

| 쌍 | 피크값 | 피크 위치 | lag 0 상관 |
|---|---|---|---|
| real pro↔user | **1.0000** | 0.00초 | 1.0000 |
| candidate1 | 0.5289 | **+10.25초** | 0.0440 |
| candidate2 | 0.5073 | **−12.21초** | −0.0010 |
| candidate3 | 0.4827 | **−10.88초** | −0.0051 |

허위 피크가 전부 **끝단 lag**(13초 영상에서 ±10~12초 = 겹침이 최소인 지점)에서
나왔습니다. 표본이 적으면 정규화 상관이 우연히 높아지기 때문이며, z-score만으로는
구분할 수 없었습니다.

**수정 — 판별 기준 3개 동시 적용**
1. 겹침 50% 이상만 후보로
2. 오프셋 범위를 짧은 쪽 길이의 30% 이내로 제한
3. **피크 상관값 자체**에 하한(0.30). z-score는 보조 기준

**수정 후**: 정답 케이스 통과(피크 0.82), candidate 1/2/3 전부 "사용 불가"(피크
0.16~0.28)로 정상 기각.

**중대한 검증 공백**: `real` 쌍의 피크 상관이 **정확히 1.0000**입니다. 즉 두 영상이
**동일한 오디오 트랙을 공유**합니다. 온셋 포락선을 채택한 이유가 "따로 촬영해 음향이
다른 경우"였는데, **정작 그 조건을 이 데이터로 검증하지 못했습니다.**

→ 그래서 **파이프라인에 연결하지 않았습니다.** `real` 쌍 오프셋이 0.000초라 붙여도
효과를 볼 수 없고, 효과를 확인할 데이터가 생긴 뒤에 붙이는 것이 맞다고 판단했습니다.

> **후속 업데이트** — 실제로 음향 환경이 다른 자연 촬영 쌍을 확보한 뒤 재검증한
> 결과는 [6.4](#64-실제-두-사람-사이-검증--앵커-라벨링) 참고. 결론을 먼저 말하면:
> 이 판단(연결 보류)이 맞았습니다 — 확보한 쌍 중 하나에서 오디오 추정이 신뢰도
> 임계값을 통과했음에도 실제로는 틀렸습니다.

### 5.8 실제 촬영본이 처음 드러낸 버그 2개

지금까지의 검증은 전부 **같은 소스에서 파생된 합성 변형본**(시간 오프셋 ≤2초)
위에서 이뤄졌습니다. 사용자가 실제로 촬영한 영상 2쌍(조명·거리·밝기 대비를
의도적으로 다르게 촬영)을 처음 파이프라인에 통과시키자, 합성 데이터로는 원리적으로
발견할 수 없었던 버그 두 개가 즉시 드러났습니다.

**버그 1 — 세로 촬영 영상의 회전 미보정**

iPhone으로 세로로 촬영한 영상은 센서가 항상 가로 프레임(예: 1920×1080)을 저장하고,
"재생 시 90도 돌려서 보여줘라"는 QuickTime Display Matrix를 메타데이터에 별도로
기록합니다. `cv2.VideoCapture.read()`는 이 매트릭스를 적용하지 않고 **원본 버퍼를
그대로** 반환합니다 — 즉 사람이 옆으로 누운 프레임이 그대로 포즈 모델에 들어가고
있었습니다.

기존 테스트 영상(`real/`, `candidates/`)은 raw 버퍼 자체가 우연히 이미 세로로
저장돼 있어 이 문제를 겪지 않았습니다. 새로 촬영한 자연 데이터가 처음으로 이 경로를
탔습니다.

- 검출: ffprobe로 Display Matrix를 읽어 회전각(0/90/180/270)을 계산하고, 프레임마다
  자동 보정
- 실측(YOLO-pose, 19프레임 샘플): 미보정 검출실패 2/19·신뢰도 중앙 0.721 → 보정 후
  실패 0/19·중앙 0.914

**버그 2 — 시간 필터가 절대 시간차를 기준으로 삼고 있었음**

첫 실행이 크래시했습니다. `compare_sequences`가 채점 가능한 쌍 0개를 반환했는데
그 케이스를 출력부가 처리하지 못했습니다. 원인을 보니 `max_time_diff`(정렬 실패
판정 기준)가 **절대 시간차**로 걸려 있었습니다. 실촬영에서는 두 영상의 녹화 시작
시점이 몇 초씩 어긋나는 것이 정상이고 psi 완화가 정상적으로 처리하는 상황인데,
절대 기준 필터는 이 정상적인 고정 오프셋 자체를 전부 "정렬 실패"로 판정해버려
채점 가능한 쌍이 전부 사라졌습니다.

DTW 경로 전체의 시간차 분포를 실제로 찍어보면 원인이 분명합니다 (natural1 예시):
중앙값 +3.31초, IQR [0.55, 3.68]초 — 대부분의 대응쌍이 하나의 고정 오프셋 근처에
몰려 있습니다.

- 수정: 기준을 **경로 전체의 중앙값 오프셋 대비 벗어난 정도**로 변경 (절대 시간차
  아님)
- 검증: 같은 데이터에서 절대 기준 ±0.6초 이내 0% → 상대 기준 57.9%로 회복. 사전에
  분포로 예측한 값(57.9%)과 실행 결과가 일치해 수정이 올바르다는 것도 함께 확인됨

### 5.9 정렬 정밀화 — 원인 진단과 두 가지 개선

[6.4](#64-실제-두-사람-사이-검증--앵커-라벨링)에서 각도 방식의 우위는 확인됐지만
±2프레임 내는 41~47%에 그쳤고, 오차가 큰 앵커가 영상 초반에 몰리는 패턴이 있었다.

**원인 진단 — 세 가설 중 하나만 살아남았다**

| 가설 | 검증 | 결과 |
|---|---|---|
| 초반 프레임의 검출 품질 저하 | 앵커 주변 유효율 vs 오차 상관 | ❌ 상관계수가 두 쌍에서 부호 반대(−0.326 / +0.188) |
| 초반 동작의 모호함 | — | 미검증 (아래와 분리 곤란) |
| **사용자가 틀린 지점이라 DTW가 헤맴** | 정답 지점 vs DTW 선택 지점의 포즈 오차 비교 | ✅ **지지됨** |

| 쌍 | 정답 지점 포즈오차 | DTW 선택 지점 | DTW가 더 비슷한 곳을 고른 비율 |
|---|---|---|---|
| natural1 (39개) | 27.6° | 24.5° | **67%** |
| natural2 (15개) | 29.9° | 26.6° | **60%** |
| natural2, 오차>0.2초인 5개 | 35.2° | 29.3° | **80%** |

**DTW는 실패한 것이 아니라 목적함수에 충실했다.** 정답보다 포즈가 더 비슷한 곳을
골랐을 뿐이다. 그리고 정렬 오차가 큰 앵커는 정답 지점의 포즈 오차 자체가 높다
(35° vs 전체 평균 27.6°) — **사용자가 그 동작을 실제로 크게 틀린 지점**이다.

> **제품 관점의 함의**: 사용자가 틀릴수록 정렬이 어긋나고, 정렬이 어긋나면 채점도
> 틀린다. **잘 추는 사람에게 정확하고 못 추는 사람에게 부정확해지는 되먹임**이
> 있는데, 정작 후자가 주 사용자다. 이는 [8장](#8-현재-한계와-미검증-영역)의
> 최상위 한계로 기록한다.

**부수 발견 — 밴드 제약이 무력화돼 있었다 (버그)**

`align()`은 경로 존재 보장을 위해 `window = max(요청값, |길이차|+1)`로 넓히는데,
두 영상 길이가 크게 다르면 이 가드가 밴드를 통째로 무력화한다.

| 쌍 | 길이차 | 요청 window=15 | 실제 적용 |
|---|---|---|---|
| natural1 | 219프레임 | 15 | **220프레임 (7.3초)** |

앞서 "window를 15~150으로 스윕해도 결과가 동일하다"고 기록한 진짜 이유가 이것이다.

**개선 ① 안무 구간을 사용자에게 입력받기 (D23)**

오프셋 자동 추정은 **세 방법이 모두 실패**했다.

| 방법 | 결과 |
|---|---|
| 포즈 DTW 1단계 추정 | natural2에서 기울기 방향조차 반대 (0.87 vs 정답 1.24) |
| 오디오 크로스코릴레이션 | natural2에서 5배 오차 (+0.88초 vs 정답 −4.76초) |
| 비율(정규화 위치) 가정 | 오프셋 성분을 원리적으로 처리 못 함 |

자동 탐지가 어려운 이유도 분명하다 — 사람은 안무 시작 전에 음악을 들으며 리듬을
타거나 자세를 잡는다. 픽셀 변화량만으로 "안무의 시작"을 판정할 수 없다.
**반면 사용자는 그 시점을 안다.**

구현 시 발견한 상호작용: **구간을 지정하면 psi를 꺼야 한다.** psi는 "구간을 모를 때"
쓰는 장치인데, 확정한 구간의 양 끝을 다시 잘라내 손해가 된다(natural2 기준
앵커 커버 10→14개, ±5프레임 내 70.0→78.6%, 최대 오차 1.25→0.27초).

**개선 ② 각속도를 정렬 신호에 추가 (D24)**

착안: 포즈가 틀려도 **움직임의 타이밍**(언제 치고 멈추고 방향을 바꾸는가)은 음악에
맞춰 유지된다. 이는 위 원리적 한계를 우회할 **독립 신호**이며, 오디오와 달리
영상만으로 얻을 수 있다.

세 갈래로 시도했다.

| 접근 | 결과 |
|---|---|
| 움직임 포락선 상호상관으로 오프셋 추정 | ❌ 오차 0.68~1.88초 |
| 자기상관으로 박자 주기 추정 | ❌ 같은 안무인데 200 BPM vs 62 BPM. 자기상관 피크 0.29~0.38로 **뚜렷한 주기 자체가 없음** |
| **각속도를 DTW feature에 직접 추가** | ✅ **채택** |

박자를 명시적으로 추정하는 대신 각속도를 자세와 함께 넣어 **DTW가 알아서 타이밍
정보를 쓰게** 했다. 가중치는 실측으로 정했다.

| 쌍 | 자세만 | 속도만 | **자세+속도 w=0.5** | 자세+속도 w=2.0 |
|---|---|---|---|---|
| natural1 ±2f | 44.7% | 42.1% | **57.9%** | 50.0% |
| natural2 ±5f | 92.9% | 71.4% | **100.0%** | 71.4% |

**속도만 쓰면 오히려 나빠지고 가중치가 크면 역시 나빠진다.** 자세가 주 신호,
속도는 보조라는 구조가 맞다. 합성 변형본 회귀도 확인 — 전부 유지(100%, trim 98.9%).

**누적 결과 (앵커 GT)**

| 단계 | natural1 ±5f | natural2 ±5f | natural2 최대 오차 |
|---|---|---|---|
| 좌표 기반 | 0% | 0% | — |
| 각도 전환 (5.2) | 71.8% | 61.5% | 1.23초 |
| + 구간 지정 | 78.9% | 78.6% | 0.27초 |
| **+ 각속도** | **81.6%** | **100%** | **0.17초** |

### 5.10 정렬 신뢰도 지표 탐색 — 실패 (중요한 부정 결과)

"정확도가 낮으면 재촬영을 안내한다"는 설계를 하려면 GT 없이 정렬 품질을 예측하는
신호가 필요하다. 앵커 52개를 정답으로 후보 5개를 측정했다.

| 후보 | 상관 | 큰오차군(>0.2초) | 작은오차군 |
|---|---|---|---|
| 매칭 지점 포즈오차 | +0.136 | 29.4° | 22.3° |
| 매칭 선명도(margin) | +0.031 | 1.62 | 1.55 |
| 유사 후보 비율 | +0.260 | 0.086 | 0.077 |
| 유효 관절율 | +0.116 | 0.991 | 0.970 |
| 정면성 | +0.041 | 0.823 | 0.649 |

**전부 예측력이 없다.** 이유가 원리적이다 — 5.9에서 확인한 실패 양상은 "불확실한
매칭"이 아니라 **"확신에 찬 틀린 매칭"** 이다. DTW가 실제로 더 비슷한 포즈를 찾아낸
것이므로 **틀린 매칭이 맞은 매칭보다 오히려 더 좋아 보인다.**

→ 국소 신뢰도 지표로는 원리적으로 감지 불가능하다. **설계 방향을 전환**했다.

1. **예방** — 시작 시점을 정밀 입력받아 오프셋 오류가 애초에 생기지 않게 (개선 ①)
2. **측정 가능한 것만 게이트** — 정렬 품질이 아니라 **영상 자체의 사용 가능성**
   (검출 실패율, 몸통 4점 확보율, 정면성). 원인이 명확하고 사용자가 고칠 수 있다

영상 품질 지표의 정상군 분포(보유 영상 8개):

| 지표 | 범위 | 이상치 |
|---|---|---|
| 관절 유효율 | 85.1~99.2% | natural2 (85~88%) |
| 몸통 4점 확보율 | 86.6~100% | natural2 user (86.6%) |
| 정면성 중앙값 | 0.413~0.646 | natural2 pro (0.413) |

**natural2가 뚜렷한 이상치**이고, 이것이 그동안 natural2에서 관측된 문제들
(채점률 31%, 오디오 추정 실패, 정렬 열세)을 상당 부분 설명한다. 품질 게이트의
실효성을 뒷받침하지만, **임계값은 아직 정할 수 없다** — 8개 모두 "분석이 되긴 한"
영상이라 실패 경계를 모른다.

### 5.11 피드백 생성

수치를 사용자가 읽을 수 있는 지적으로 바꾸는 마지막 단계 (`src/feedback.py`).

**출발점의 문제**: `compare_sequences` 출력은 0.27초 간격 87개 프레임이다.

| 문제 | 처리 |
|---|---|
| 양이 과함 | 연속 프레임을 구간으로 병합 (0.5초 이내 연속이면 한 구간) |
| 한 동작이 여러 건으로 | 같은 부위 기준 병합 |
| 방향 없음 | `pairwise_error`를 확장해 **부호 있는 차이** 반환 → "더 펴세요/굽히세요" |
| 부위 간 비교 불가 | 부위마다 가동 범위가 다름(전완 중앙 29.9° vs 몸통 9.1°). **영상 자체의 부위별 분포**로 정규화 |

**구현 중 발견 — 부위별 병합만으로는 부족했다.** 1차 결과에서 상위 5개 중 4개가
같은 시간대(8.3~11.8초)에 몰렸다. 한 시점에 평균 5.4개, 최대 11개 부위가 동시에
걸린다. → **신체 그룹**(왼팔/오른팔/왼다리/오른다리/상체)으로 재병합.

**점수 폐기** — 환산 상수가 임의값이라 절대값에 의미가 없었다. 대신 **틀린 동작
개수**를 센다.

**신뢰 불가 구간 분리** — 프레임 평균 오차 ≥90도면 지적하지 않는다. 근거: natural1
분포에서 p95=49도인데 p99에서 119도로 급격히 튀고 최대 178도다. 178도는 물리적으로
정반대 방향이라 같은 동작을 비교한 결과로 보기 어렵다. **틀린 피드백을 주는 것보다
"확인 어려움"으로 빼는 편이 낫다**는 판단이다.

```
── 피드백 ── 틀린 동작 47개 (부위별 125개를 묶음)
 1. [ 7.8~11.5s] 오른다리 — 오른쪽 무릎을 더 펴세요   평균 22도, 심각도 3.8
 2. [ 7.8~12.0s] 왼다리  — 왼쪽 무릎을 더 굽히세요
 ...상위 10개
 확인 어려움 2구간 (총 0.3초) — 평가 제외
```

### 6.4 실제 두 사람 사이 검증 — 앵커 라벨링

지금까지 D1(각도 채택)의 근거는 전부 [5.2](#52-비교-표현--좌표에서-관절-각도로)의

증명하지 못한 채 남아 있었습니다.** 사람이 직접 대응 시점을 표시한 정답(앵커)이
있어야만 확인 가능한 질문이었습니다.

**GT**: 자연 촬영 쌍 2개(natural1, natural2). 조명·촬영 거리·밝기 대비를 의도적으로
다르게 촬영해 실제 서비스 조건에 가깝게 만들었습니다. 앵커는 39개·15개, 각각
사람이 "동작(포즈) 기준"으로 라벨링했습니다 — 박자가 아니라 안무 구조상 대응되는
지점을 기준으로 삼았고, 사용자가 동작을 틀리게 실행한 지점도 "원래 그 동작이
나왔어야 할 지점"에 표시했습니다. (이유: DTW 자체가 포즈 유사도로 시간을
재배열하므로, 정답도 같은 정의를 따라야 정답으로서 의미가 있습니다. "포즈가
비슷해 보이는 곳"을 정답으로 삼으면 원형 논리가 됩니다.)

**결과**

| natural1 (n=39) | 좌표 | 3.668초 | 0.0% | 0.0% |
| natural2 (n=15) | **각도** | **0.100초** | 46.7% | **66.7%** |
| natural2 (n=15) | 좌표 | 2.668초 | 0.0% | 0.0% |

**좌표 방식은 사실상 정렬을 전혀 못 했습니다.** 두 쌍 모두 좌표의 오차가 그 쌍의
고정 오프셋(녹화 시작 시점 차이)과 거의 같은 크기입니다 — 시간 워핑을 전혀 하지
않고 프레임을 순서대로 그대로 매칭했다는 뜻입니다. 카메라 거리·밝기가 다른 두
사람의 좌표를 직접 비교하니 실제 포즈 유사도 신호가 촬영 조건 차이에 완전히
묻힌 것으로 보입니다.

**각도 방식은 서로 다른 안무·다른 촬영 조건의 두 쌍에서 독립적으로 일관된
결과**(±5프레임 내 67~72%)를 보였습니다. 우연으로 보기 어려운 재현성입니다.
D1의 결정이 실제 조건에서도 유효하다는 최초의 직접 증거입니다.

**⚠️ 완벽하지는 않습니다.** ±2프레임 내는 41~47%에 그칩니다. 오차가 큰 앵커를
들여다보면 두 쌍 모두 **영상 초반**(natural1: pro 프레임 122~299, natural2: pro
프레임 195~272)에 몰려 있습니다. psi를 키워 재검증했으나(natural1 psi=120프레임,
natural2 psi=150프레임) 뚜렷한 개선이 없었습니다 — natural1은 ±5프레임 내 비율이
오히려 71.8%→69.2%로 약간 떨어졌고, natural2는 psi 상한 제약으로 앵커 수가
15→13개로 줄면서 비교 자체가 불안정해졌습니다. **원인 미규명.** 후보로 남겨둔
것: (a) 안무 초반의 포즈가 더 모호해 포즈 기반 매칭이 어려움, (b) 사용자가 동작을
틀리게 실행한 지점(안무 구조상 정답과 포즈 유사도 기반 DTW의 판단이 갈릴 수 있는
지점)이 초반에 몰려 있을 가능성, (c) 초반 프레임의 검출 품질 차이. 앵커 라벨과
대조하면 확인 가능하나 아직 진행하지 못했습니다.

**부수 결과 — 오디오 대 포즈 오프셋 추정, 앵커로 최종 판정**

앵커로 "진짜" 오프셋(앵커 쌍들의 시간차 중앙값)을 직접 계산할 수 있게 되면서,
[5.7](#57-오디오-사전-정렬)에서 미해결로 남겨둔 오디오 대 포즈 불일치를 판정했습니다.

| 쌍 | 오디오 추정 | 포즈 DTW 추정 | **앵커 기준 실제값** |
|---|---|---|---|
| natural1 | −3.692초 | +3.65초 | **+3.647초** |
| natural2 | +0.882초 | −3.77초 | **−4.756초** |

natural1은 오디오·포즈 두 방법 모두 실제값과 0.01초 이내로 정확했습니다. **natural2는
오디오 추정이 완전히 틀렸습니다** — 부호부터 반대이고 크기도 5배 이상 차이납니다.
포즈 DTW는 부호는 맞지만 여전히 약 1초 벗어나 있습니다.

이것이 의미하는 바: `audio_align.py`의 신뢰도 임계값(`min_peak=0.30`)은 natural2의
피크 상관값 0.390을 통과시켜 "사용 가능"으로 판정했지만 실제로는 틀렸습니다. 이
임계값은 명백히 틀린 답(다른 곡 등)을 걸러내는 데는 유효했지만([5.7](#57-오디오-사전-정렬)의
음성 대조군에서 확인), **임계값을 겨우 넘는 경계 사례의 정확성까지는 보장하지
못합니다.** 필요조건이지 충분조건이 아닙니다. 오디오 정렬을 파이프라인에 연결하지
않은 기존 판단이 사후에 정당화된 셈입니다.

### 6.5 최종 파이프라인 구성

```
영상 A, B
  │
  ├─ fps 독출 (범위 검사, 비정상이면 30 폴백)  ← 두 영상 각각
  │
  ├─ 포즈 추정 (yolo11x-pose 권장)
  │    └→ 좌표 + 신뢰도
  │
  ├─ PoseSequence 구성

  │    └─ 유효성 마스크 (신뢰도 임계 미만 = 존재하지 않음)
  │
  ├─ FeatureSet 구성 — 관절 각도 14종
  │    ├─ 몸통 축 중앙값으로 카메라 롤 자가 보정
  │    └─ 정면성 지표 계산 (기록만)
  │
  ├─ [정렬용] 짧은 구멍 보간 → (cos,sin) 인코딩 → dtw_ndim (window + psi)
  │                                                        │
  │                                                     대응 경로
  │                                                        │
  └─ [채점용] 마스킹 유지 ────────────────────────────────┘
             │
             ├─ 2단 프레임 게이트 (몸통 4점 필수 + 유효 비율)
             ├─ 시간 필터 (두 영상 fps 각각 사용)
             └─ 유효 항목만 평균 → 각도 오차(도)
```

## 7. 예측이 빗나간 사례

의도적으로 별도 장으로 분리했습니다. **틀린 예측을 지우지 않는 것**이 이 프로젝트의
기록 원칙이고, 어디서 직관이 어긋났는지가 다음 판단의 근거가 되기 때문입니다.

### 7.1 "SOTA 모델이 이길 것이다"

- **예측**: RTMPose가 본선 유력, ViTPose가 정확도 천장을 보여줄 것
- **결과**: 둘 다 yolo11x를 이기지 못함. RTMPose-l은 기존 yolov8n보다도 뼈 안정성이 나빴음(0.0150 vs 0.0143)
- **배운 것**: 벤치마크 명성과 특정 도메인·특정 지표에서의 성능은 별개다. 단, 모델 크기가 맞춰지지 않았다는 단서가 있어 일반화는 금물

### 7.2 "전완 오차는 손목 노이즈가 증폭된 것이다"

- **관찰**: 전완·팔꿈치만 오차가 유독 큼(중앙 30°, 나머지 5~16°)
- **가설**: 손목 키포인트가 부정확한데 전완은 짧은 분절이라 작은 픽셀 오차가 큰 각도 오차로 증폭된다
- **검증**: 대조군에서 feature별 노이즈 바닥 측정 → **전완 0.5°, 허벅지 0.6°로 사실상 동일.** 카메라 기울임 반응도 3.0° vs 2.4°로 비슷
- **결론**: 가설 폐기. 전완 feature 자체는 다른 것들만큼 안정적이므로, 실제 쌍의 30°는 **두 댄서의 실제 팔 동작 차이**이거나 **그 구간의 정렬 오류**. 둘의 구분에는 앵커가 필요 → **미해결로 남김**

### 7.3 "서브샘플링이 최대 오차를 절반 이상 날려버린다"

- **관찰**: ×6에서 최대 오차가 −54.8%
- **경보**: 큰 오차 순간을 놓치고 있다
- **검증**: 채점쌍 수도 455 → 47로 줄어드는 점을 통제 (동일 분포에서 같은 개수 무작위 추출 1000회)
- **결론**: **경보를 절반 정정.** 최대값 하락은 대부분 표본 축소 효과(대조군 편차 ±17에 묻힘)로 유의하지 않음. 다만 **p90은 일관되게 −2σ**로 실제 정보 손실이 맞음. 크기는 처음 생각보다 작지만 실재함

### 7.4 "psi를 크게 걸면 실제 대응 구간을 건너뛸 것이다"

- **우려**: 끝점 완화를 너무 넉넉히 주면 맞아야 할 구간까지 스킵할 수 있다
- **검증**: 전체가 정상 대응하는 변형 3종에서 psi=100 적용
- **결과**: 손해 0건. offset에서는 오히려 개선(0.074초 → 0.001초)
- **유의**: 변형본 4종·영상 1개에서만 확인했으므로 이론적 위험은 남아 있음. 3.0초는 위험과 커버리지 사이의 잠정 절충

## 8. 현재 한계와 미검증 영역

### 8.1 합성 데이터의 한계 — 부분 해소됨

**Phase 2까지의 검증은 전부 합성 데이터 위에서 이뤄졌습니다.** 변형본은 원본과 같은
영상에서 나왔으므로 두 포즈 시퀀스가 거의 동일했습니다.

- ✅ 증명한 것: 정렬 기계가 의도대로 작동하는가 (**정확성**)
- ❌ (당시) 증명 못 한 것: 다른 댄서 사이에서도 작동하는가 (**난이도**)

당시 지적했던 데이터 한계 세 가지와 현재 상태:

| 한계 | 영향 | 상태 |
|---|---|---|
| pro/user 프레임 수가 정확히 동일 | 시간 어긋남이 없어 정렬 개선을 실제 쌍에서 확인 불가 | ✅ 해소 — 자연 촬영 쌍(natural1/2) 확보, [6.4](#64-실제-두-사람-사이-검증--앵커-라벨링) |
| 두 영상의 오디오가 완전히 동일(상관 1.0000) | 음향 차이 조건이 미검증 | ✅ 해소 — natural1/2는 독립 녹음. 부수로 오디오 임계값의 허점도 발견 |
| 테스트 영상이 쉬움(검출 실패 0프레임) | 겹침 대응 능력이 스트레스되지 않음 | ⚠️ **미해소** — natural1/2도 검출 실패 0프레임이었음. 겹침이 많은 영상은 아직 없음 |

**남은 공백**: 겹침(occlusion) 스트레스 테스트용 데이터는 여전히 없습니다. 겹침이
많은 영상(브레이킹 등)을 하나 더 확보하면 이 축이 완전히 해소됩니다.

### 8.3 미구현

- **정렬은 서브샘플 / 채점은 전체 프레임 분리** — 5.6의 결론이지만 구현 전
- **오디오 오프셋 파이프라인 연결** — 보류를 유지. natural2에서 임계값 통과에도
  실제로는 틀린 사례가 나와, 연결하더라도 포즈 기반 추정과의 교차검증 없이는
  쓸 수 없다는 게 [6.4](#64-실제-두-사람-사이-검증--앵커-라벨링)에서 확인됨
- **다중 인물 선택·추적** — 가정 A1이 깨지는 실서비스 조건
- **VFR 영상 대응** — 가정 A6
- **카메라 이동 감지** — 가정 A5
- **정렬 오차의 초반 편중 원인 분석** — [6.4](#64-실제-두-사람-사이-검증--앵커-라벨링)에서
  새로 발견

### 8.4 서비스 반영 상태

핵심 연구 결과는 서비스의 `ai-server/engine`에 이식했습니다.

| 연구 결과 | 서비스 반영 |
|---|---|
| 포즈 백엔드 | MediaPipe에서 **YOLO-pose**로 교체 |
| 자세 표현 | 좌표 유사도에서 **관절 각도 + 결측 마스크**로 교체 |
| 시간 정렬 | fastdtw에서 **`dtw_ndim` + 밴드 + 각속도 보조**로 교체 |
| 구간 처리 | 사용자가 지정한 시작·끝 시각을 분석에 반영 |
| 처리 시간 | 기본 `stride=2`로 포즈 추정 프레임을 줄임 |

`feedback.py`와 `sequence.py`는 연구·서비스 코드가 같고, `dtw_compare.py`와
`features.py`는 import 경로만 다릅니다. 포즈 추출은 배포 환경(aarch64, CPU 전용)에
맞춰 `ai-server/engine/pose_yolo.py`에서 별도로 구현했습니다. 서비스 이식 과정과
운영 환경에서 발견한 문제는 [엔지니어링 노트](engineering-notes.md)에 기록했습니다.

[8.3](#83-미구현)의 항목은 현재도 서비스에 반영되지 않은 후속 과제입니다.

| D4 | 프레임 게이트 2단 | 몸통 4점은 신뢰도가 아니라 계산 가능 여부의 문제 |
| D5 | 몸통 축 중앙값으로 롤 자가 보정 | 롤은 분포를 일정하게 shift시키는 상수 오프셋 |
| D6 | 몸통 회전은 미보정, 정면성만 기록 | 같은 안무면 양쪽이 같이 회전해 상쇄됨 |
| D7 | `dtw_ndim` 채택, fastdtw 폐기 | 1D API 오용이 원인. fastdtw는 근사·저속 |
| D8 | fps는 양쪽 각각, 1~240 벗어나면 30 폴백 | 0/NaN/90000 같은 값이 실제로 나옴 |
| D9 | 보간은 5프레임 이하만 | 긴 구간 보간은 데이터 날조 |
| D10 | 다중 인물 선택은 보류 | 현재 데이터에 배경 인물 없음 |
| D11 | yolo11x-pose 채택 | SOTA 2종이 이기지 못함(예측 실패) |
| D12 | 관절 개수는 모델 선택 기준 아님 | 각도 feature가 코어 12개만 사용 |
| D13 | 3D 계열은 보류 | 시간 제약. MediaPipe world landmark 실험은 저비용 |
| D14 | 발끝 평가 보류 | COCO17에 발끝 없음 |
| D15 | hybrid 폐기 (코드는 보존) | crop 구현 문제로 진단 완료 |
| D16 | 각도는 (cos,sin) 인코딩 | 순환량이라 경계에서 튐 |
| D17 | 정면성은 게이트 안 함 | 적정 임계값 미검증 |
| D18 | top-down 자체는 문제 아님 | 라이브러리는 종횡비 유지, hybrid는 직접 crop |
| D19 | psi 끝점 완화 기본 활성 | 손해 0, 이득 2 |
| D20 | 영상의 회전 메타데이터를 읽어 자동 보정 | iPhone 세로 촬영본은 `cv2.read()`가 회전을 적용하지 않아 사람이 옆으로 누운 채 처리되고 있었음. 신뢰도 중앙값 0.72 → 0.91 |
| D21 | `max_time_diff`를 절대 시간차가 아닌 **경로 중앙값 오프셋 대비 상대값**으로 | 실촬영은 녹화 시작 시점이 몇 초씩 어긋나는 게 정상인데, 절대 기준이 이 정상 오프셋 자체를 전부 걸러내 채점 가능 쌍이 0개가 되는 크래시가 있었음 |
| D23 | **안무 구간을 사용자에게 입력받는다** (`--pro-start-sec` 등). 구간 지정 시 psi는 끈다 | 오프셋 자동 추정 3가지가 모두 실패. 사람은 시작 시점을 안다. psi는 구간을 모를 때 쓰는 장치라 확정 후엔 양 끝을 다시 잘라 손해 |
| D24 | **각속도를 DTW 입력에 보조 성분으로 추가** (가중치 0.5) | 포즈가 틀려도 움직임 타이밍은 유지된다. 실측 w=0.5가 최선이고 속도만 쓰면 나빠짐 — 자세가 주, 속도가 보조 |
| D25 | 피드백은 **신체 그룹 단위 구간**으로. 점수 대신 **틀린 동작 개수**. 90도 초과는 "확인 어려움"으로 분리 | 부위별로 내면 한 시점이 평균 5.4개로 중복 지적됨. 점수 환산 상수가 임의값. 90도 초과는 정렬 실패 가능성이 큼 |

### 9.2 재현 방법

```bash
cd model-research
python3.10 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 1) 검증 데이터 생성 (변형본 + dense GT)
python -m tools.make_variants --video data/videos/real/user_dancer.mp4

# 2) 정렬 정확도 (5.1, 5.4)
python -m tools.eval_alignment --mode variant \
    --gt data/variants/user_dancer__local0.50.gt.json --windows 15 none
python -m tools.eval_alignment --mode variant \
    --gt data/variants/user_dancer__trim.gt.json --psi 100 --windows none

# 3) feature 촬영조건 불변성 (5.2)
python -m tools.eval_invariance --variants 'data/variants/*reencode*.gt.json' \
    'data/variants/*zoom*.gt.json' 'data/variants/*shift*.gt.json' 'data/variants/*roll*.gt.json'

# 4) 모델 품질 비교 (5.5)
python -m tools.eval_pose_quality --video data/videos/real/user_dancer.mp4 \
    --models yolo:models/yolov8n-pose.pt yolo:models/yolo11x-pose.pt mediapipe:1

# 5) 서브샘플링 (5.6)
python -m tools.eval_subsample --gt data/variants/user_dancer__local0.50.gt.json
python -m tools.eval_subsample_scoring --pro data/videos/real/pro_dancer.mp4 \
    --user data/videos/real/user_dancer.mp4

# 6) 오디오 정렬 (5.7)
python -m tools.audio_align --a data/videos/real/pro_dancer.mp4 \
    --b data/videos/real/user_dancer.mp4

# 전체 파이프라인
python -m src.main --pose-backend yolo --feature angle
```

### 9.3 코드 구성

**파이프라인 (`src/`)**

| 파일 | 역할 |
|---|---|
| `video_utils.py` | fps 독출 및 범위 검사 |

| `dtw_compare.py` | `dtw_ndim` 정렬 + psi 완화 + 마스킹 채점 |
| `main.py` | 실행부, 시각화 |
| `pose_yolo.py` / `pose_hybrid.py` / `pose_vitpose.py` / `pose_rtmpose.py` | 백엔드 |

| 파일 | 역할 |
