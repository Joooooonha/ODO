## 서비스 기능

기준 영상(프로 댄서)과 내 연습 영상을 올리면, **어느 대목에서 어떤 동작이 어긋났는지**를
구간 단위로 짚어줍니다.

- **나란히 비교** — 두 영상이 같은 안무 지점에 맞춰 함께 움직입니다.
  기준 영상은 원래 속도 그대로 흐르고 **내 영상이 늘어나고 줄어들며 따라갑니다.**
  내 영상이 빨리 감기면 그 대목에서 내가 느렸던 것입니다.
- **박자 어긋남 그래프** — 기준 대비 얼마나 앞섰는지/뒤처졌는지의 누적 차이.
- **다듬을 구간 목록** — 시간 순이 기본이고, 심각도 순위는 배지로 함께 보여줍니다.
  구간을 누르면 그 대목만 0.5배속으로 반복 재생합니다.

**완전 자동 채점이 아닙니다.** 빠르게 비교하고 어디가 틀렸는지 편하게 보여주되,
무엇부터 고칠지 결정하는 것은 사람에게 맡기는 **반자동** 구조입니다.
정렬 실패가 "불확실한 매칭"이 아니라 "확신에 찬 오답"으로 나타난다는 실측이
이 방향의 근거입니다.

## 해결하고자 한 문제

대학교에서 처음 춤을 배웠기 때문에 혼자 연습하며 자기 동작을 판단하기 어려운 경험을
알고 있었습니다. 2년 차에 팀장을 맡아 후배들과 공연을 준비하면서, 제가 없는 시간에도
후배가 스스로 동작을 점검할 방법을 만들고 싶었습니다. "느낌이 다르다"를 말로 옮기는
방식도 사람마다 달라, 기준 영상과 연습 영상을 직접 비교하는 도구를 만들었습니다.

처음에는 비전 모델로 두 영상을 분석해 보면서 예외를 찾았습니다. 같은 안무라도 시작
시점과 속도가 달라 다른 동작끼리 비교되는 문제를 발견해 DTW를 적용했고, 이후에는
촬영 거리·각도 차이가 좌표 오차로 계산되는 문제를 관절 각도 표현으로 분리했습니다.

## 분석 설계

### 비교 문제의 분해

문제를 세 축으로 나눴습니다.

| 축 | 문제 | 접근 |
|---|---|---|
| **시간** | 같은 안무라도 시작 시점과 속도가 다름 | DTW 정렬 |
| **촬영 조건** | 카메라 거리·각도·체형이 다름 | 좌표 대신 **관절 각도** |
| **표현** | 프레임별 수치는 사람이 못 읽음 | 구간 병합 + 방향 문구 |

### 포즈 추정 모델

초기 프로토타입에서는 단일 댄서의 자세를 가볍게 추출하기 위해 관절 수와 처리 속도를
기준으로 MediaPipe를 선택했습니다. 현재 엔진을 다시 설계하면서 실제 비교에는 어깨·팔꿈치·
손목·엉덩이·무릎·발목의 핵심 관절만 사용한다는 점을 확인했고, 관절 수를 모델 선택
기준에서 제외했습니다.

이후 YOLO, MediaPipe, ViTPose, RTMPose 계열을 뼈 길이 안정성·시간적 흔들림·처리 속도로
비교했습니다. 정답 키포인트가 없는 영상이어서 이 값들을 정확도라고 부르지 않고,
라벨 없이 확인할 수 있는 **품질의 필요조건**으로 사용했습니다.

| 단계 | 실행 환경과 판단 | 선택 |
|---|---|---|
| **연구** | Apple M2·MPS에서 후보 모델 비교. `yolo11x-pose`가 뼈 안정성 0.0127로 가장 낮았지만, 쉬운 영상 한 편의 대리 지표라는 한계가 있음 | `yolo11x-pose`를 품질 상한으로 기록 |
| **서비스** | Fedora Asahi Linux·CPU 전용. `yolo11x-pose`는 프레임당 2.068초로 운영하기 어려웠고, `yolo11n-pose`는 0.091초 | `yolo11n-pose` 채택 |

MediaPipe 0.10.x의 Linux aarch64 휠이 없다는 배포 제약도 있었지만, 더 중요한 기준은
**검증한 엔진과 서비스하는 엔진을 일치시키는 것**이었습니다. 연구와 서비스가 서로 다른
포즈 모델을 쓰던 상태를 YOLO 계열로 통일하고, 가속기 도입 시 대형 모델을 다시 검토하도록
남겼습니다.

### 분석 파이프라인

```mermaid
flowchart TD
    A["영상 회전 보정"] --> B["YOLO 포즈 · 17개 관절"]
    B --> C["관절 유효성 마스크"]
    C --> D["14개 관절 각도"]
    D --> E["다변량 DTW · 각속도"]
    E --> F["오차 구간 병합 · 방향 피드백"]
```

- iPhone 영상의 회전 메타데이터를 먼저 보정해 포즈 모델에 옆으로 누운 프레임이 들어가지 않게 했습니다.
- 보이지 않는 관절을 `0`으로 채우면 두 영상에서 모두 누락된 관절이 완벽히 일치한 것으로 계산되므로, 유효성 마스크로 비교 대상에서 제외했습니다.
- 좌표 대신 몸통 기준 관절 각도를 사용해 카메라 위치·거리·체형 차이가 동작 오차로 섞이는 것을 줄였습니다.
- 포즈 유사도만으로 안무 구조를 구분하기 어려운 구간은 사용자가 시작 지점을 지정하고, 각속도를 함께 사용해 움직임의 타이밍을 보완했습니다.

## 시스템 구조

인증·권한·작업 상태와 CPU를 오래 사용하는 영상 분석을 서로 다른 실행 환경으로 분리했습니다.

```mermaid
flowchart TD
    A["브라우저"] -->|HTTPS| B["Cloudflare"]
    B --> C["EC2 · Spring Boot (앱 서버 2대)"]
    C --> D[(PostgreSQL)]
    C -->|Tailscale| E["Mac mini · FastAPI"]
    A -->|presigned PUT·GET| F["Cloudflare R2"]
    E <-->|영상·결과| F
```

| 결정 | 이유 |
|---|---|
| **Spring과 FastAPI를 분리** | 포즈 추정·DTW는 파이썬 생태계에 있고, 인증·권한·트랜잭션은 JVM이 편합니다. 한쪽에 몰면 어느 한쪽이 불편해집니다 |
| **분석은 집에 있는 맥미니** | 포즈 추출이 CPU를 오래 씁니다(30초 영상 2개에 약 92초). EC2에서 하려면 인스턴스를 훨씬 키워야 하는데, 하루 몇 건을 위해 상시 비용을 낼 이유가 없습니다 |
| **맥미니를 공인 IP에 올리지 않음** | 집에 있는 홈서버입니다. Cloudflare → EC2까지만 공개하고, 그 뒤는 Tailscale 내부망으로만 닿습니다 |
| **영상이 EC2를 지나가지 않음** | 브라우저가 R2로 직접 올리고 맥미니가 R2에서 직접 받습니다. 수십 MB가 작은 인스턴스의 대역폭·디스크를 쓰지 않고, Cloudflare 프록시의 요청 본문 100MB 제한도 거치지 않습니다 |
| **맥미니에 저장소 키를 주지 않음** | Spring이 요청마다 짧은 presigned URL만 발급합니다. 홈서버가 뚫려도 얻을 수 있는 것이 곧 만료될 URL 몇 개뿐입니다 |
| **R2 (S3 아님)** | egress 요금이 0입니다. 가장 큰 트래픽이 맥미니의 영상 다운로드와 사용자의 결과 조회인데, S3였다면 그 둘이 곧바로 비용이 됩니다 |
| **앱 서버가 2대가 된 뒤에도 분석은 전체 동시 1건** | 2026-10에 채팅을 넣으며 앱 서버를 2대로 늘렸습니다. 분석은 맥미니 한 대가 하므로, 두 서버가 각자 보내면 동시 분석이 2건이 됩니다. PostgreSQL advisory lock으로 두 서버를 합쳐 1건만 맥미니에 보내고, 나머지는 기다립니다 |

### 비동기 처리 흐름

분석에 약 2분이 걸려 HTTP 요청을 붙잡고 있을 수 없으므로 **비동기 + 폴링**입니다.

```mermaid
sequenceDiagram
    participant U as 브라우저
    participant S as Spring API
    participant R as R2
    participant A as FastAPI 분석 서버
    U->>R: 영상 직접 업로드
    U->>S: 구간 지정·분석 요청
    S-->>U: 202 Accepted
    S->>A: Tailscale 내부 요청
    A->>R: 영상 다운로드
    A->>A: 포즈 추출·정렬·피드백
    A->>R: 결과 업로드
    U->>S: 진행률 폴링
    S-->>U: 상태·결과 URL
```

**결과물 URL은 저장하지 않고 조회할 때마다 새로 만듭니다.** presigned URL은 만료되므로
DB에 넣으면 얼마 못 가 열리지 않습니다. DB에는 객체 키만 둡니다.

### 저장소 구성

| 경로 | 역할 |
|---|---|
| `ai-server/engine/` | 분석 엔진 (`model-research`에서 이식) |
| `ai-server/main.py` | FastAPI — 분석 전용, 아무것도 보관하지 않음 |
| `model-research/` | 방법론 실험·검증 코드 |

정렬·특징 계산 코드(`dtw_compare.py`, `features.py`, `feedback.py`, `sequence.py`)는
`model-research`와 **import 경로만 다르고 내용이 같습니다.** 측정한 것과 서비스하는
것이 같아야 문서의 검증 수치를 서비스의 수치라고 말할 수 있기 때문입니다.
포즈 추출(`pose_yolo.py`)만 배포 환경(aarch64, CPU 전용) 때문에 다시 썼습니다.

## 검증

검증은 **초기 프로토타입의 사용 가능성**과 **현재 분석 엔진의 기술 정확성**을 구분했습니다.

| 단계 | 평가 방법 | 확인한 것 | 아직 말할 수 없는 것 |
|---|---|---|---|
| **초기 프로토타입** | 간단한 기본기 동작의 결과를 영상과 나란히 보며 정성 평가 | 후배가 혼자 자세를 점검하는 보조 도구로 사용할 가능성 | 복잡한 동작까지의 일반화, 사용자 효과의 정량 수치 |
| **현재 분석 엔진** | 합성 dense GT와 자연 촬영 영상의 앵커 라벨로 정량 측정 | 시간 정렬과 촬영 조건 차이를 다루는 방식의 정확성 | 피드백 문구의 교육적 타당성, 겹침이 많은 동작의 품질 |

기능을 늘리기 전에 **"이게 맞나"를 확인할 방법**부터 만들었습니다. 원본 영상을 알려진
양만큼 변형해(시간 오프셋, 배속, 렌즈 왜곡, 재인코딩) **정답을 아는 데이터**를
합성하고, 그걸로 정렬 정확도를 쟀습니다.

| 측정 | 결과 |
|---|---|
| 정렬 정확도 (앵커 ±5프레임) | 71.8% → **78.9%** (구간 지정) → **81.6%** (각속도 보조) |
| 뼈 안정성 (낮을수록 좋음) | yolo11x **0.0127** / yolov8n 0.0143 / MediaPipe Full 0.0189 |
| 프레임 솎기 (stride=2) | 분석 **44% 단축**, 지적 구간 상위 10개 **100% 재현** |

**측정이 예측을 여러 번 뒤집었습니다.** "SOTA 모델이 이길 것", "손목 노이즈가 원인일 것"
— 둘 다 틀렸습니다. 틀린 예측을 지우지 않고 기록으로 남겼습니다.

## 문제 해결

<details>
<summary><b>1. 다차원 시계열에 맞지 않는 DTW API</b></summary>

정렬 결과가 이상한데 원인을 못 찾다가, `dtaidistance.dtw.distance()`가
**1차원 스칼라 시계열 전용 API**라는 것을 알게 됐습니다. 거기에 다차원 특징을
flatten해서 넣고 있었고, 그러면 **프레임 경계가 사라집니다** — 34번 프레임의 마지막
값과 35번 프레임의 첫 값이 같은 축 위에 놓입니다.

`dtw_ndim.warping_path()`로 바꾸자 정렬이 정상 동작했습니다. 라이브러리가 에러를
내지 않고 그럴듯한 숫자를 돌려주고 있었던 것이 발견을 늦췄습니다.

</details>

<details>
<summary><b>2. 입력 순서에 따른 비결정적 포즈 추출</b></summary>

사용자가 같은 영상을 다시 분석하면 "틀린 동작 45개"가 "52개"가 됐습니다.

프레임별 키포인트를 해시로 찍어 비교한 결과:

| 처리 순서 | 기준 영상 | 연습 영상 |
|---|---|---|
| 기준 → 연습 (1회차) | `626ef14a` | `c4499a27` |
| 기준 → 연습 (2회차) | `626ef14a` | `9244b72c` ← 다름 |
| 연습만 단독 (2회) | — | `9949adf0` (동일) |

**단독으로 처리하면 완전히 결정적인데, 해상도가 다른 영상을 앞에서 처리하면
비결정적이 됐습니다.** 차이는 반올림 수준이 아니라 868프레임 전부, 최대 121.9픽셀
(프레임 높이의 6.4%)이었습니다.

영상마다 별도 프로세스에서 추출하도록 바꿔 해결했습니다. 추출이 영상당 수십 초라
프로세스 생성 비용(1~2초)은 묻힙니다.

</details>

## 검증 과정의 판단

- **검증 기준의 선행** — 처음엔 기능부터 늘렸는데 "이게 맞나"를 확인할 수
  없어 멈췄습니다. 정답을 합성하는 방법을 찾고 나서야 버그 3개를 정량적으로 잡았습니다.
- **동작 여부와 정확성의 구분** — 서비스로 옮기며 나온 문제들은 전부 에러 없이 200을
  반환하던 것들이었습니다. 로그만 봐서는 다 정상이었습니다.
- **문서와 테스트의 일치** — "운영에서는 개발용 로그인이 비활성"이라고
  적어두고 검증하지 않았는데, 테스트를 써 보니 그대로 열려 있었습니다. 검증되지 않은
  기록은 오히려 안심하게 만들어 더 위험합니다.

## 현재 한계

- **정렬이 실패했는지 자동으로 알 수 없습니다.** 신뢰도 신호 5종을 시험했지만 전부
  정렬 오차를 예측하지 못했습니다(상관 0.03~0.26). 실패가 "불확실한 매칭"이 아니라
  "확신에 찬 오답"으로 나타나기 때문입니다. 지금은 오차가 임계를 넘는 구간을
  "확인 어려움"으로 분리해 **지적하지 않는** 방식으로만 다룹니다.
- **촘촘한 정렬 정답은 합성 데이터입니다.** 자연 촬영 영상 2쌍은 사람이 표시한 앵커로
  보완했지만, 전체 프레임의 정답과 겹침이 많은 브레이킹 영상은 아직 없습니다.
- **피드백은 정성 평가 단계입니다.** 초기 기본기 프로토타입에서 결과를 눈으로 확인했지만,
  현재 엔진의 피드백 문구가 실제 연습에 얼마나 도움이 되는지는 정량화하지 못했습니다.
- **이론상 처리량 상한이 시간당 약 30건입니다.** 분석 서버가 동시 1건, 건당 약 2분이라는
  현재 구성으로 계산한 값이며 부하 테스트로 보장한 처리량은 아닙니다.
  늘리려면 큐와 워커 풀이 필요합니다.
- **다중 인물을 처리하지 않습니다.** 배경에 사람이 있으면 첫 번째 검출을 그대로 씁니다.
