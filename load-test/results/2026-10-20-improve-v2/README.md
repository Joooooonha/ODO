# 읽음 개선 측정 v2 (측정 환경 v2) — 기준선 v2(R0)·R1 v2 다시 재기

> **측정 환경 v2(nginx 2 CPU)에서 무릎점은 v1과 같았다.** R0(W=0) 800~1,200, R1(W=500) 1,600~2,000이다. nginx throttle은 모든 단계에서 0.0%로, v1 R2를 무효로 만든 앞단 포화는 이 환경에서 다시 나오지 않았다.
> **R1의 과부하(2,000 이상)는 메시지 처리 스레드 한계다.** 두 서버 합쳐 초당 약 2,000건에서 처리량이 멈췄고(send 평균 ≈ 3.9ms × 스레드 4개 × 2대), 앱 CPU는 서버당 1.45/2코어에서 멈췄다. 호스트 CPU는 최대 9.2/16코어로 90%(14.4)에 닿지 않았다.
> **R0(W=0)의 과부하(1,200)는 앱 CPU 포화다.** 서버당 1.99/2코어, send 평균 7.6ms, Hikari 대기 최대 51이었다.
> 불변식 위반 0, 읽음 위치 멈춤 0(여섯 실행 모두).

- 코드·설정: **`24f3185`**. 윈도우를 그 커밋으로 맞추고 측정했다. jar는 `0bcbaa0` 코드 빌드(SHA256 `8eac11d8…d6a1`)로, 두 커밋 사이에 서버 코드 변경은 없다
- CI(완료 확인 후 기록): 44a7ab5 success(39393608699), 0bcbaa0 success(39394660464), 24f3185 success(39400403715)
- 환경 v2 = 기준선 환경 + nginx `cpus: 2`. 가짜 서버(보정 전용)는 샤드 4개·5 CPU이고, 단계마다 호스트 전체 CPU를 기록한다(`/proc/stat`, WSL2 VM 논리 CPU 16개)
- 설정: `configs/v2-r0.json`(W=0; 400·700·800·1,200·1,600), `configs/v2-r1.json`(W=500; 400 … 4,200), 반복 실행 `configs/v2-rep-w500.json`(400·700·800·1,600·2,000·2,400). R0 반복 실행은 400·700·800만 잰다
- 원본: `results/raw/win/v2/{v2-r0, v2-r0-rep2·3, v2-r1, v2-r1-rep2·3}/`, 보정 `calibration-2026-10-20T08-32-02-329Z`(W=0), `calibration-2026-10-20T08-41-28-836Z`(W=500), recorder `recorder-cgroup.jsonl`

## 10/20 준하 결정 (판정 규칙)
1. 생성기는 그대로 둔다. 판정은 기존 규칙을 따른다(D-07: 오차 한도 + guard band).
   - 쓸 수 있는 범위는 보정에서 생성기 ELU < 0.9인 단계다. **W=500은 4,200 이하, W=0은 1,200 이하**
   - 범위 밖 단계는 "생성기 포화로 무효"로 적는다
2. 표에는 단계별 보정 오차를 함께 적는다. 개선은 차이가 그 단계의 보정 오차보다 클 때만 주장한다
3. 호스트 CPU는 실행마다 확인한다. 과부하 단계에서 호스트 CPU가 90%(14.4코어)를 넘으면 "호스트 경합 가능"으로 적는다 → 이번에는 해당 단계가 없다
4. 무릎 근처 단계(R0 700·800, R1 700·800·1,600·2,000·2,400)는 세 번 재서 중앙값을 쓴다. 그 밖의 단계는 한 번 잰다

## 작업 3 — 메시지 1건 처리 시간 분해 (v2-diag, W=500, `0bcbaa0` 지표)

진단 실행은 v2·R1 설정에 pg_stat_statements만 켰다(`compose.pgss.yml`, 진단 실행에만). 원본은 `results/raw/win/v2/v2-diag/`(pgss.txt 포함)이다.

| 단계(`chat.send.stage`) | 1,000건/초 | 1,600건/초 |
|---|---|---|
| **commit** (커밋 = WAL 디스크 동기화 대기) | **1.80ms (69%)** | **2.91ms (77%)** |
| seq(순번 행 UPDATE) + member(멤버 확인) + insert | 0.56 | 0.57 |

- SQL 실행 시간 합(pg_stat_statements)은 메시지 1건당 약 0.13ms다. INSERT 0.07~0.08, chat_room UPDATE 0.04, 멤버 SELECT 0.01, FK 확인 0.01이다. DB에서 SQL을 실행하는 시간은 작다
- 측정 DB 디스크의 `pg_test_fsync` 결과는 fdatasync 1.90ms/op(약 525회/초)다(`wal_sync_method = fdatasync`, `synchronous_commit = on`, `commit_delay = 0`)
  - 1,000건/초의 commit 1.80ms는 디스크 동기화 1회와 맞는다
  - 1,600건/초에서는 앞 동기화가 끝나기를 기다리는 몫이 더해져 2.9ms가 된다
- **한계: 디스크 동기화 1.9ms는 측정 장비(WSL2 위 ext4) 값이고, 운영 디스크는 확인하지 않았다(운영 서버 접근 금지).** 운영 디스크의 동기화가 더 빠르면 commit 몫과 아래 3-2의 효과가 둘 다 작아진다

### 멈춤 지점 B 결정 (10/20 준하)
- **3-1(1건 시간 줄이기)은 하지 않는다.** 메시지 1건 처리 3~4ms는 전달 기준(p95 100ms)에 비하면 사용자 지연에 영향이 없다. 문제는 지연이 아니라 스레드 4개의 처리량 상한(4 / 3.9ms × 2대 ≈ 2,050건/초)이다. 그래서 1건 시간을 줄이지 않고, 동시성으로 동시 커밋을 같은 디스크 동기화에 묶어(그룹 커밋) 처리량을 올린다 → 3-2
- **A. 메시지 트랜잭션만 `synchronous_commit = off` — 검토 후 기각.**
  - 예상 효과: commit 1.8~2.9ms → 약 0.1ms
  - 기각 근거 1: DB 장애(앱이 아니라 PG·OS) 때 확인 응답을 받은 메시지를 잃는다(최근 최대 약 3 × wal_writer_delay = 0.6초분)
  - 기각 근거 2: 같은 WAL에 있던 chat_room.last_seq도 함께 되돌아가므로 DB 안에는 빈틈·중복이 없다. 하지만 **순번이 재사용된다.** 이미 그 순번을 받은 클라이언트에서는 순번 기반 중복 제거와 충돌한다(새 메시지를 이미 본 것으로 버린다)
- **D. 여러 메시지를 트랜잭션 하나로 묶기 — 하지 않는다.** 구현이 크고 세션 순서를 따로 지켜야 해서 위험이 크다
- **B. `commit_delay` — 설정은 바꾸지 않는다.** 3-2 결과를 보고 효과가 있을지 의견만 적는다(아래)
- **E. Redis 발행을 커넥션 반납 뒤로 — 조건부.** 3-2에서 스레드 8개일 때 Hikari 대기가 생기면 적용해 켬/끔을 비교한다
  - 같은 스레드에서 동기로 실행한다(비동기 금지). 같은 방의 발행 순서는 지금과 같게 유지한다
  - Hikari 대기가 없으면 하지 않는다

(커밋/초는 DB 전체 xact_commit이다. 메시지 저장 말고 읽음 보고 등의 트랜잭션도 들어 있다.)

- 디스크 동기화는 횟수가 초당 약 500회(= 1 / 1.9ms)에서 더 늘지 않는다. 그 대신 **동기화 1회에 묶이는 커밋 수가 2.6 → 8.3으로 늘었다. 그룹 커밋이 일어난다는 뜻이다**
- 4개일 때는 동시에 커밋을 기다리는 트랜잭션이 많아야 4 × 2대라서, 1회당 5.3에서 처리량이 막혔다. 8개로 늘리자 더 많이 묶여 처리량이 올랐다
- 커밋 대기(`commit` 단계)는 8개에서 3.0~3.3ms(4개는 2.9~3.0)다. 1건 시간은 거의 그대로이고, 한꺼번에 처리하는 수가 늘었다. 발행(`publish`)은 0.26 → 0.49ms(3,000)로 조금 늘었다(Redis·아웃바운드 부하)
- **Hikari 대기가 생겼다(E 조건 충족).** 8개에서 2,000~3,000일 때 대기 최대 6~16, 획득 평균 0.10~0.15ms(4개는 0.01~0.02), `begin` 단계 0.02 → 0.08ms다. 풀 10개를 인바운드 8개와 읽음 보고(Tomcat)가 나눠 쓴다

**B(`commit_delay`) 의견 — 효과 없을 것으로 본다, 바꾸지 않기를 권한다.** WAL 동기화는 이미 초당 약 500회 × 1.9ms ≈ 95% 시간 동안 쉬지 않고 돈다. 앞 동기화를 기다리는 동안 다음 커밋들이 저절로 모여서, 묶음이 이미 생긴다(위 표 1회당 4.7~8.3). `commit_delay`는 동기화가 한가할 때 일부러 기다려 묶는 설정이다. 여기서는 묶음은 거의 늘지 않고, 기다린 만큼 지연만 더한다. 또 3,600 이상의 상한은 앱 CPU라서, 커밋을 더 묶어도 무릎은 올라가지 않는다. (운영 디스크가 더 빠르면 동기화가 한가해져 판단이 달라질 수 있다. 운영 디스크는 확인하지 않았다.)

## 작업 3-2 조건부 E — 발행을 커넥션 반납 뒤로 (`2eddafc`, 스레드 8개, `CHAT_PUBLISH_AFTER_RELEASE`)

`chat.send.publish-after-release`(기본 끔)를 켜면, 사람이 보낸 메시지의 Redis 발행을 트랜잭션이 끝나 커넥션을 돌려준 뒤에 **같은 스레드에서 동기로** 한다. 처리 메서드가 돌아오기 전에 발행이 끝난다. 그래서 세션 차례 처리와 같은 방 발행 순서는 지금과 같다(테스트 `ChatPublishAfterReleaseTest`). 켰는지는 지표 `chat_redis_publish_connection_total{state}`로 확인했다. 켬 3회는 전부 released(앱마다 약 74만~77만), 끔은 전부 held였다.

켬 3회(e-on ×3)를 같은 커밋 끔 1회(e-off)와 비교했다. 앞 커밋 끔 3회(t32-t8 ×3)도 함께 적는다(t32-rep-w500, 1,000·1,600·2,000·2,400·3,000).

| r | 전달 p95 켬 [세 값] → 중앙값 | 끔 e-off (같은 커밋) | 끔 t32-t8 ×3 | 보정 오차 |
|---|---|---|---|---|
| 1,600 | 11.15 / 11.28 / 10.86 → 11.15 | 10.01 | 10.98 / 13.75 / 9.98 | 5.04 |
| 2,000 | 17.95 / 18.54 / 18.43 → 18.43 | 18.34 | 33.12 / 24.26 / 18.98 | 7.05 |
| 2,400 | 40.99 / 39.84 / 38.02 → 39.84 | 41.70 | 47.33 / 50.24 / 48.83 | 7.21 |
| 3,000 | 109.6 / 101.0 / 106.2 → 106.2 판정 보류 | 103.2 판정 보류 | 133.6 / 240.4 / 134.3 실패 | 10.22 |

| r | 커넥션 보유 평균 켬 / 끔(e-off, t32-t8 ×3) | Hikari 획득 평균 켬 / 끔 | 대기 최대 켬 / 끔 |
|---|---|---|---|
| 2,400 | **3.41~3.45 / 3.74~3.82** | 0.065~0.090 / 0.095~0.100 | 1~7 / 0~23 |
| 3,000 | **3.60~3.63 / 3.96~4.13** | 0.065~0.135 / 0.115~0.150 | 0~15 / 7~16 |

- 커넥션 보유는 발행 시간만큼(0.35ms, 약 9%) 줄었다. 켬과 끔의 값 범위가 겹치지 않는다
- 하지만 **전달 지연과 무릎은 보정 오차 안에서 같다.** 같은 커밋 끔과의 차이는 2,400에서 1.9ms, 3,000에서 3.0ms다(오차 7.2·10.2). 3,000은 켬·끔 모두 판정 보류(100ms ± 오차)다
- Hikari 획득 평균은 끔에서도 0.1~0.15ms다. 메시지 1건 4.5ms에 비해 작고, 켬과 끔의 범위가 겹친다. 대기가 생기긴 했지만 처리량을 막을 만큼은 아니었다
- 끔 t32-t8(`fd7d6d8`)과 e-off(`2eddafc`)는 코드가 같은데도(설정 꺼짐) 2,000·3,000에서 e-off가 낮았다. 실행 사이 흔들림이 이 정도 있다. 그래서 E 판정은 같은 커밋 끔과 비교했다
- 메시지 WAL 묶음(동기화 1회당 커밋)은 켬·끔 같다(3,000에서 7.54~7.58 / 7.56)
- 불변식 위반·읽음 멈춤 0. 걸린 시간 실행마다 14분 31~33초

## 작업 3-3 — 남길 것 판단 (3-1은 하지 않음)

판단 기준: 무릎이 올라가거나, 1건 처리·Hikari가 보정 오차를 넘게 좋아지고, 불변식 위반이 0이어야 남긴다.

| 항목 | 판단 | 근거 |
|---|---|---|
| 3-1 (1건 시간 줄이기) | **하지 않음** (멈춤 지점 B 결정) | 1건 3~4ms는 전달 기준 100ms에 비해 사용자 지연에 영향 없음. 문제는 처리량 상한 |
| A `synchronous_commit=off` | 검토 후 기각 | 확인 응답 받은 메시지 유실, 순번 재사용 |
| B `commit_delay` | 설정 그대로 | 위 의견 |
| D 묶음 트랜잭션 | 하지 않음 | 구현 크고 세션 순서 위험 |
| **3-2 스레드 8개** | **남긴다** | 무릎 1,600~2,000 → 2,400~3,000(2,000: 2,090 → 24ms, 오차 7.05를 크게 넘음). 불변식 위반 0. 대가는 Hikari 획득 대기 0.01 → 0.1~0.15ms와 커밋 대기 +0.1~0.3ms |
| E 발행 반납 뒤 | **남기지 않는다** (설정은 기본 끔 그대로, 기준선에서 끔) | 커넥션 보유는 0.35ms 줄었지만, 전달·무릎·Hikari 획득이 보정 오차·실행 흔들림 안에 있다 |

이후 측정(기준선 v3, 작업 4~6)은 `CHAT_WS_INBOUND_THREADS=8`, `CHAT_PUBLISH_AFTER_RELEASE=false`로 한다. 코드 기본값(0 = CPU × 2, 끔)은 바꾸지 않았다. 운영 기본값은 정하지 않았다.

**걸린 시간(3-2·E):** t32-t8 20분 00초, t32-t4 14분 33초, t32-t8-rep2 14분 33초, t32-t8-rep3 14분 32초, e-on 14분 31초, e-off 14분 33초, e-on-rep2 14분 33초, e-on-rep3 14분 33초. 측정만 약 2시간 2분이다(코드·테스트·CI 제외).
