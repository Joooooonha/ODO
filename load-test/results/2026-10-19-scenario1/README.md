## 판정 규칙

1. 성공 기준: 메시지 전달·확정 p95 ≤ 100ms, 읽음 반영 p95 ≤ 1초
2. 측정 유효: 같은 설정(비율·r)의 보정 오차 p99 ≤ 기준의 5%(전달·확정 5ms, 읽음 반영 50ms). 표의 괄호가 그 단계의 보정 오차 p99
3. guard band: 오차가 한도를 넘어도 |측정 p95 − 기준| > 보정 오차면 통과/실패 판정은 유효. 기준에서 오차 이내일 때만 "판정 보류"
4. **개선 전후 비교는 차이가 그 단계 보정 오차보다 클 때만 개선 효과로 주장한다**
5. 측정기 포화(= 측정 불가): 생성기 이벤트 루프 사용률 ≥ 0.9 또는 받은 방 프레임 < 받아야 할 것의 99%. 프로세스 CPU는 압축 해제 스레드 때문에 1코어를 넘을 수 있어 단독 기준으로 쓰지 않는다
6. 보정 오차 = 생성기가 잰 값 − 넣은 지연 − 가짜 서버의 같은 종류 프레임 처리 시간(압축 포함). 보정은 서버 몫 8 CPU(가짜 서버 4 + stress 4)를 채운 상태에서

**앱 2대 합 CPU(코어) ≈ 0.079 + 0.00209 × 메시지/초 + 0.00141 × 읽음 보고/초**

- 메시지 1건 ≈ **2.1ms CPU**(저장 + 발행 + 구독자 20명에게 MESSAGE 20프레임), 읽음 보고 1건 ≈ **1.4ms CPU**(HTTP + 갱신 + 스냅샷 + 발행 + READ 20프레임)

### 20:0 읽음 처리 시간의 구성(기존 지표)
| | 1:19 (r=10·100) | 20:0 (r=5·10) |
|---|---|---|
| 읽음 처리 `chat.read.duration` 평균 / p99 | 1.3~1.6 / 3.2~5.7 | **4.1~4.2** / 15~18 |
| 그중 스냅샷 `chat.read.snapshot.duration` 평균 | 0.24~0.29 | 0.30 |
| 커넥션 쥔 시간 `hikaricp.connections.usage` 평균 | 1.0 | **3.6** |
| 커넥션 획득 평균 | 0.0~0.04 | 0.0 |

- 20:0에서 늘어난 ~3ms는 스냅샷(0.3ms)이 아니라 **커넥션을 쥔 동안의 나머지**: 갱신 트랜잭션(UPDATE + 커밋) + 발행. 메시지 한 건에 20명이 동시에 보고 → 갱신·커밋 20건이 겹친다. 잠금 대기는 0(1초 표본)이고 획득 대기도 0이라, 기다림보다는 동시 커밋(WAL 쓰기)일 가능성이 크다 — **기존 지표로는 갱신·커밋·발행을 더 나눌 수 없다**(나누려면 구간 타이머가 필요, 개선 후보에 적음)
- 20:0 r=1의 p99 29ms는 JVM 새로 띄운 첫 단계(커넥션 획득 최대 87~108ms, 쥔 시간 최대 140~176ms)라 예열 영향이다. 안정 상태 p99는 15~18ms
- 같은 스레드 문제("읽음 구간 계산이 메시지 전달을 밀어내는가"): 리스너 처리 p99 MESSAGE ≤ 1.9ms · READ ≤ 1.4ms, 대기 p99 ≤ 6.3ms(무릎 전까지 r에 따라 커지지 않음) → **이 범위에서는 밀어내지 않는다**

## 측정 도구 자체 검증 — 보정이 잡은 것·놓친 것

1. **가짜 서버 재사용 버그**(`edebfb6`): 경우마다 가짜 서버를 다시 설정할 때, 앞 경우의 타이머가 다시 설정한 뒤에 울려 새 방에 큰 읽은 위치를 넣었다 → 보고가 전부 건너뛰어져 읽음 반영이 10~12초로 보였다. 측정기를 먼저 측정해서 잡았다. 같은 계열로 늦게 도착한 보고도 막았다(`0f2ac3e`, 실제 서버와 같은 `last_seq` 검사)
2. **보정 조건 불일치로 놓친 사례 — 웹소켓 압축**: 실제 서버(Tomcat)는 `permessage-deflate`를 협상하는데 가짜 서버는 하지 않아, 첫 보정에는 생성기의 압축 해제 비용이 없었다. 같은 부하에서 생성기 CPU가 실제 서버 상대로 3.5배(20:0 r=10: 0.19 → 0.68)였고, 보정에서 유효였던 20:0 r=20·30과 10:10 r=40이 실측에서는 측정기 포화였다

| 20:0 r=10 | 2.25 · 7.78 / 100% / 0.19 | 25.0 · 21.9 / 100% / 0.56 |
| 20:0 r=20 | 10.14 · 10.20 / 100% / 0.37 | **1,896 · 1,891 / 92% / 1.0 (포화)** |

교훈: 보정은 측정 대상과 **같은 협상 조건**(압축·프로토콜 옵션)이어야 한다. 루프 지연 기준도 이 포화를 못 봤다 → 포화 판정에 루프 사용률·받은 프레임 비율을 넣었다. 압축 보정에서 가짜 서버(Node) 자신이 압축을 따라가지 못하는 한계도 드러나(1 CPU → 4 CPU로 늘림, 전체 2만 프레임/초 이상의 규모 보정은 여전히 가짜 서버 한계), 그 위의 생성기 유효성은 실측의 포화 판정으로 지킨다

## 기록만 (개선 후보·백로그, 기준선에는 넣지 않았다)
- A6 OSIV 끄기(2-3에서 찾은 "요청 하나가 커넥션 둘" 함정)
- 운영 nginx `worker_connections`·`worker_rlimit_nofile`을 함께 올리기(한쪽만 올리면 다른 쪽에 걸린다). 운영 설정은 바꾸지 않았다
- `MaxRAMPercentage` 또는 `-Xmx` 명시(운영 힙이 메모리 25% 기본값)
- 읽음 처리 구간 타이머(갱신·커밋·발행 분리) — 20:0 비용의 원인을 지표로 나누려면 필요
- 20:0 비용 자체: 메시지 1건 = 보고 20건 = 스냅샷 20번 = READ 400프레임(디바운스·묶음·보는 사람에게만 등은 개선 후보, 기준선에는 없음)
