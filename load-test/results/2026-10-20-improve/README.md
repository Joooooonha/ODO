# 읽음 개선 측정 — R0·R1·R2 끝, R2 과부하 단계에서 멈춤

> **R1(묶기 B만)은 성공 기준을 모두 만족했다.** 무릎점이 약 820 → 1,600~2,000건/초로 약 2배 이상 이동했고, 읽음 반영 p95는 약 480ms(기준 1초 안)였으며 불변식 위반은 0이었다.
> 같은 800건/초에서 앱 CPU가 45% 줄었다(3.23 → 1.74코어). 새 첫 병목은 CPU가 아니라 **메시지 처리 스레드 4개 × 1건 3.9ms**(서버당 약 1,025건/초)다.
> **R2(벌크헤드 A만, K = 12)는 1,200·1,600 단계에서 측정 nginx가 81%·89% throttle돼 무효다(멈춤 조건 5).** 그래서 R3(B + A)은 하지 않았다.
> 원인은 W = 0일 때 거절된 보고가 500ms 뒤 다시 나오는 동작이다. 앱의 일은 줄지만 앞단 프록시를 지나는 요청 수는 줄지 않는다([채팅 딥다이브](../../../docs/chat-deep-dive.md) 5.2).
> 설계 근거는 [채팅 딥다이브](../../../docs/chat-deep-dive.md).

## 10/20 결정 (이번 진행의 규칙)
1. 무릎 근처 비교 단계를 **700**으로 바꾸고 700·800은 **세 번 재 중앙값**으로 비교한다. 1,200 이상 과부하 단계는 한 번
   - **새 기준선**: 800 = R0·D1·새 R0(R0b)의 중앙값, 700 = R0b·rep2·rep3의 중앙값(첫 R0·D1에는 700이 없어 새로 세 번 쟀다), 1,200 = 첫 R0 한 번
   - 반복 실행은 본 실행과 같은 순서(400 → 700 → 800)로 재서 단계 순서 효과를 맞췄다. 그래서 R0 800 값이 다섯 개 있다(중앙값은 결정대로 세 개로, 다섯 개로 해도 36.3으로 같다)
2. **K = 12**(두 서버 같은 값). R2 800에서 거절률 > 1%면 2배 → 세 번 모두 1% 미만이라 조정 없음
3. 승인: 포화 판정의 "보내기 대기열 작음" = 단계 중 최대 < 100(기준선 생성기 포화 단계 최대 8~11의 10배), 5xx 재전송

### 단위 비용 다시 맞추기 · 용량 모델 갱신
- 기준선 (나)에서는 보고 수가 늘 메시지 수의 2배라 메시지 항과 보고 항이 같이 움직였다(결합 회귀 구간이 넓었던 이유). R1은 보고가 초당 400으로 고정이라 둘이 갈라진다
- R1 (나) r = 200~1,600, 12개 단계(본 실행 + 반복): 앱 CPU(2대 합) = 0.883 + **1.05ms × 메시지/초**(보고 400 고정)
- 같은 메시지 수에서 기준선과 비교하면 보고 1건의 비용이 나온다:
  - r = 810: 기준선 3.14 − R1 1.74 = 1.40코어 / 보고 1,200건 = **1.17ms**
  - 기준선 전체 기울기(메시지 1건 + 보고 2건 = 3.58ms) − 1.05ms = 2.53ms → **보고 1건 1.27ms**
  - r = 200은 두 실행 모두 보고 400이라 앱 CPU가 0.99 / 1.01코어로 같다(검증)
- 갱신한 식: **앱 CPU(2대 합) ≈ 0.14 + 1.05ms × 메시지/초 + 1.2~1.3ms × 보고/초.** 메시지 1건당 비용 중 읽음 몫은 54%가 아니라 약 70%였다(기준선 회귀가 메시지 항을 크게 잡았다)
- 용량 모델의 예측(2.5절, 옛 식) vs 실측:
  - r = 1,200: 옛 식 2.70코어 vs 실측 2.18코어
  - r = 1,600: 옛 식 3.42코어 vs 실측 2.54코어
  - 옛 식은 메시지 항이 과대라 CPU를 과대 예측했다. 그래서 CPU 기준 무릎(4코어의 80%)은 R1 식으로 ≈ 2,200건/초다
  - 실제로는 그 전에 인바운드 실행기 상한(≈ 2,050)이 먼저 온다

## 멈춘 이유와 정할 것
- **멈춤 조건 5:** 측정 대상이 아닌 컨테이너(측정 nginx, CPU 1개 상한)의 throttle(81%·89%) 때문에 R2의 핵심 단계(1,200, 성공 기준 단계)가 무효다
- 멈추기 전에 이미 돌던 R2 반복(700·800)은 nginx 영향이 없는 단계라 끝까지 쟀다. R3은 시작하지 않았다
- 정할 것:
  1. R2를 어떻게 다룰지. 셋 중 하나를 고른다
     - (가) R2는 "A 단독은 W = 0 재전송 때문에 과부하에서 앞단을 흔든다"는 결과로 기록하고 R3(B + A)로 간다. B가 켜져 있으면 재전송이 창 간격에 묶여 보고 요청이 초당 약 400건으로 고정된다(R1에서 확인)
     - (나) 측정 nginx 상한을 올려(1 → 2 CPU) R2 1,200·1,600을 다시 잰다. 기준선 환경과 달라지므로 R0 1,200도 같은 조건으로 다시 재야 한다
     - (다) W = 0일 때 429를 받으면 다시 보내지 않거나 간격을 늘리도록 규칙을 바꾼다. 코드 변경 → 새 커밋·CI·재측정
     - 추천은 (가)다. 운영에서 켤 조합은 B + A이고, R2의 실패 모습 자체가 "A는 B와 함께"라는 설계 근거가 된다
  2. 다음 병목(인바운드 실행기 4스레드 × 1건 3.9ms ≈ 2,050건/초)을 이번 범위에서 다룰지. 설계 당시에는 스레드를 늘리지 않는 이유(커넥션 경쟁)를 적어 두었다.
     R1에서 Hikari 대기는 0이라, 스레드를 늘렸을 때 커넥션 경쟁이 실제로 먼저 오는지 잴 수 있다
  3. 운영 기본값(병합 전): 제안은 B = 500. A는 B와 함께 켤 때만 K = 12(R3 결과를 보고 정함)

## 포화 판정 수정 규칙 — 기준선 전 단계에 다시 적용

- 원래 규칙: 이벤트 루프 사용률 ≥ 0.9 또는 받은 방 프레임 < 99% → 생성기 포화
- 오분류 사례: (나) r=1,200·1,600은 받은 프레임 97.1%·98.4%라 원래 규칙으로는 "생성기 포화 = 무효"인데, 모자란 프레임은 서버가 늦게 보낸 것
  (서버 throttle 95~97%, 인바운드 대기 p99 ≈ 10초, 생성기 루프 사용률 0.80·throttle 0)
- 수정 규칙: 생성기 포화 = 루프 사용률 ≥ 0.9, 또는 (받은 프레임 < 99% 이면서 서버 쪽 신호가 작음). 서버 쪽 신호가 작다 = 앱 throttle < 5%(두 대 모두),
  인바운드 대기 p99 < 100ms, 보내기 대기열(`executor_queued_tasks{clientOutboundChannelExecutor}`) 최대 < 100. 서버 포화 = 받은 프레임 < 99% + 서버 쪽 신호가 큼.
  둘 다면 판정 불가. "보내기 대기열 작음"의 숫자(100)는 따로 정했다 — 기준선 생성기 포화 단계의 최대가 8~11이라 그 10배
- 다시 적용한 결과(`stage-report-revised.json`): **바뀐 칸은 (나) r=1,200·1,600뿐**(생성기 포화 → 서버 포화). (나) r ≤ 800과 시나리오 1 전 단계는 그대로.
  시나리오 1 기록에는 루프 사용률·받은 프레임 칸이 없어(그 뒤에 넣은 지표) 결과 문서의 READ 받음/기대(20:0 r=20·30: 89%·59%, 10:10 r=40: 85%)와
  서버 신호(throttle 0, 인바운드 p99 ≤ 2ms, 보내기 대기열 ≤ 11)로 판정 — 두 규칙 모두 생성기 포화
- R0 r=1,200도 원래 규칙 "생성기 포화", 수정 규칙 "서버 포화"
