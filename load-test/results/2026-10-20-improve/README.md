### r=800의 차이는 어디서 왔나 (진단, 멈춘 뒤 R1 대신 한 것)
- 단계 안 시계열(5초 간격): 18:13:00~18:14:35는 인바운드 대기 최대 ≤ 26ms·실행기 대기열(인바운드·아웃바운드 중 큰 쪽) ≤ 62로 평소와 같다. **18:14:40부터 약 20초**만 실행기 대기열 725,
  인바운드 대기 최대 1.5초, 읽음 동시 처리 54, Tomcat 사용 중 80, Hikari 대기 65 → 그 뒤 회복. 그 순간 docker stats로 app1·app2가 **동시에 약 208%**(상한)
- GC 멈춤 최대 12~26ms(원인 아님), 잠금 대기 0, sql_exporter 세션 수 일정 → 원인을 기존 지표로 특정하지 못했다(부하가 순간 몰렸는지, 호스트 쪽 간섭인지)
- 같은 커밋·같은 설정으로 400·800만 두 번 더 쟀다:

## 스레드 풀별 CPU (R0, 서버당 코어) — 우선순위 역전을 숫자로

| r | 인바운드(메시지 SEND) | Tomcat(읽음 HTTP + 웹소켓 프레임 읽기) | 아웃바운드(보내기·압축) | Redis 수신 | 그 밖의 Java | 합 / 프로세스 |
|---|---|---|---|---|---|---|
| 400 | 0.11 | 0.29 | 0.24 | 0.06 | 0.14 | 0.84 / 0.92 |
| 800 | 0.18~0.19 | 0.58~0.60 | 0.40~0.41 | 0.09 | 0.22 | 1.48 / 1.61 |
| 1,200 | 0.19~0.21 | **0.76~0.79** | 0.48~0.50 | 0.09 | 0.24 | 1.79 / 1.99 |

- 800 → 1,200(보낸 메시지 +32%): Tomcat +0.18코어(+32%), **인바운드 +0.02코어(+9%)**. CPU가 모자라자 늘어난 몫의 대부분을 Tomcat 쪽이 가져갔고
  메시지 스레드는 거의 늘지 못했다 → 인바운드 대기 10초. "읽음이 메시지보다 CPU를 더 가져간다"가 추정이 아니라 측정값이 됐다
- 주의: Tomcat 스레드는 읽음 HTTP만이 아니라 웹소켓 프레임 읽기(SEND 프레임을 받아 인바운드로 넘기기)도 한다 → Tomcat 몫 전부가 읽음은 아니다
- 합과 프로세스 CPU의 차이(0.08~0.2코어)는 GC·JVM 내부 스레드(ThreadMXBean에 없다)

## 포화 판정 수정 규칙 (준하 승인) — 기준선 전 단계에 다시 적용

- 원래 규칙(2-4): 이벤트 루프 사용률 ≥ 0.9 또는 받은 방 프레임 < 99% → 생성기 포화
- 오분류 사례: (나) r=1,200·1,600은 받은 프레임 97.1%·98.4%라 원래 규칙으로는 "생성기 포화 = 무효"인데, 모자란 프레임은 서버가 늦게 보낸 것
  (서버 throttle 95~97%, 인바운드 대기 p99 ≈ 10초, 생성기 루프 사용률 0.80·throttle 0)
- 수정 규칙: 생성기 포화 = 루프 사용률 ≥ 0.9, 또는 (받은 프레임 < 99% 이면서 서버 쪽 신호가 작음). 서버 쪽 신호가 작다 = 앱 throttle < 5%(두 대 모두),
  인바운드 대기 p99 < 100ms, 보내기 대기열(`executor_queued_tasks{clientOutboundChannelExecutor}`) 최대 < 100. 서버 포화 = 받은 프레임 < 99% + 서버 쪽 신호가 큼.
  둘 다면 판정 불가. "보내기 대기열 작음"의 숫자(100)는 지시서에 없어 정했다 — 기준선 생성기 포화 단계의 최대가 8~11이라 그 10배
- 다시 적용한 결과(`stage-report-revised.json`): **바뀐 칸은 (나) r=1,200·1,600뿐**(생성기 포화 → 서버 포화). (나) r ≤ 800과 시나리오 1 전 단계는 그대로.
  시나리오 1 기록에는 루프 사용률·받은 프레임 칸이 없어(그 뒤에 넣은 지표) 결과 문서의 READ 받음/기대(20:0 r=20·30: 89%·59%, 10:10 r=40: 85%)와
  서버 신호(throttle 0, 인바운드 p99 ≤ 2ms, 보내기 대기열 ≤ 11)로 판정 — 두 규칙 모두 생성기 포화
- R0 r=1,200도 원래 규칙 "생성기 포화", 수정 규칙 "서버 포화"

## 단위 비용 결합 회귀의 신뢰구간 (`analysis/unit-cost-bootstrap.py`)

시나리오 1 r ≥ 5 + (나) r ≤ 800, 15개 단계, 단계 재표집 bootstrap 20,000번, 95% 구간.

| 모형 | 메시지(ms/건) | 보고(ms/건) | 프레임(µs/개) | 방 크기 항(ms/보고/인원) | R² |
|---|---|---|---|---|---|
| M3: a + b·메시지 + c·보고 | 1.78 [1.38, 2.63] | 1.02 [0.63, 1.39] | — | — | 0.995 |
| M4: M3 + d·프레임 | 1.73 [−0.31, 3.37] | 1.06 [0.25, 2.56] | −3.2 **[−90, +30]** | — | 0.995 |
| M5: M3 + e·보고·(인원 − 4) | 1.75 [0.56, 7.99] | 1.04 [−2.09, 1.83] | — | −0.001 [−0.07, 0.16] | 0.995 |

- **"프레임당 비용 ≈ 0"은 구간상으로 0을 포함**하고, 상한도 약 30µs다. 보정 때의 "서버 프레임당 약 76µs"는 서버 CPU 전체를 프레임 수로 나눈 **평균**(일의 비용 포함)이라
  한계 비용이 아니다 — 이 구간(상한 30µs)과 맞지 않는 것이 그 증거다. 단 구간이 넓어서 "프레임 비용이 작다"까지만 말할 수 있다
- 방 크기에 비례하는 부분은 **분리되지 않는다**(구간이 0을 포함하고 넓다). 방 크기가 4·20명 두 가지뿐이고 보고 수와 함께 움직이기 때문이다
  → 결론은 "**테스트 범위(4~20명)에서는**"으로 한정한다
- R1(묶기로 보고 수가 메시지 수와 따로 움직인다)이 들어오면 보고·메시지·프레임이 더 잘 갈라질 것이다 — R1 이후 다시 맞춘다
