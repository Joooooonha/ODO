- **r=1,200·1,600은 서버 포화로 판정**했다. 승인된 포화 규칙의 "받은 프레임 < 99%"에 걸리지만, 모자란 프레임은 서버 인바운드 대기열(10초)에 밀려 측정 창 안에 나가지 못한 것이다(서버 throttle 97%, 생성기 루프 사용률 0.80 < 0.9, 생성기 throttle 0). 규칙을 "서버 대기열이 작은데 받은 프레임이 모자랄 때"로 좁히는 것을 제안한다(보고서 5절)
- 서버가 소화한 최대량: **메시지 ≈ 1,070건/초 + 읽음 보고 ≈ 2,070건/초**(목표 1,200·1,600이어도 같음 — 전송 창 50이 차서 생성기가 더 못 보냄, `send:blocked`)
- **포화 때 메시지가 읽음보다 먼저 무너진다**: r=1,200에서 전달 p95 ≈ 10초인데 읽음 반영 p95 = 70ms. 메시지 SEND는 웹소켓 인바운드 실행기(스레드 4개, 무제한 FIFO), 읽음 보고는 HTTP(Tomcat 스레드 최대 200)로 들어와 CPU가 모자랄 때 HTTP 쪽이 스레드 수로 이긴다. 리스너 스레드(같은 스레드 문제)가 아니라 **실행기 크기의 비대칭**이 원인이다

## 용량 모델과 비교

### 예측 범위가 640 ~ 3,400건/초로 넓었던 이유
시나리오 1은 모든 일이 20명에게 퍼져 "일 1건당" 비용과 "프레임 1개당" 비용을 나눌 수 없었다(프레임 = 20 × 일). (나)는 퍼짐이 4라 두 가정이 크게 갈린다.
| 가정 | (나) 메시지 1건의 비용 | 예측 무릎(앱 3.2코어) |
|---|---|---|
| 비용이 **일**에 붙는다(시나리오 1 계수 그대로: 메시지 2.09 + 보고 2 × 1.41) | 4.91ms | ≈ 640건/초 |
| 비용이 **프레임**에 붙는다(76µs × 12프레임) | 0.91ms | ≈ 3,400건/초 |

### 실측
- 80% 지점: 810건/초에서 3.14코어(79%) → **무릎 ≈ 820건/초**, 100%는 ≈ 1,070건/초에서
- **"일" 가정에 맞았다**(실측은 그 예측보다 25~30% 높은 쪽, "프레임" 가정의 1/4). 두 시나리오를 합친 회귀에서 프레임 항은 −3µs(0과 구별 안 됨)

**결합 단위 비용**(시나리오 1 r ≥ 5 + 시나리오 2 r ≤ 800, 17단계, R² 0.995):
**앱 2대 합 CPU(코어) ≈ 0.142 + 1.78ms × 메시지/초 + 1.02ms × 읽음 보고/초** → (나) 메시지 1건 3.82ms → 예측 무릎(3.2코어) 801건/초, 4코어 포화 1,010건/초 — 실측(820 / ≈ 1,070)과 맞는다

### 선형 모델이 어긋난 곳
| (나) r | 실측 | 시나리오 1 모델 | 결합 모델 |
|---|---|---|---|
| 50 | 0.45 | 0.35 (−23%) | 0.35 |
| 200 | 0.99 | 1.08 (+10%) | 0.92 |
| 400 | 1.78 | 2.06 (+16%) | 1.69 |
| 800 | 3.14 | 4.03 (**+28%**) | 3.21 |
| 1,200 | 3.97(상한) | 5.25 (+32%) | 4.17 |

- 시나리오 1 모델(앱 0.08~0.42코어 구간, 방 크기 20에서 맞춤)을 10배 넘게 늘리자 **크게 잡았다**: 시나리오 1의 "일 1건" 비용에는 방 크기에 비례하는 일(스냅샷 20행, 구간 계산, 20명 위치 JSON, 구독자 20명 찾기)이 들어 있어 4명 방에서는 그만큼 싸다. 낮은 r(50)에서는 기본값(JVM 배경 0.08 vs 0.14코어)이 작게 잡혀 반대로 어긋났다
- 무릎 근처에서 CPU는 4코어에 붙어 더 오르지 않고(선형 예측 4.17 → 실측 3.97), 지연은 선형이 아니라 **대기열로 폭발**한다(r=800 p99 43ms → r=1,200 p50 8.7초)

## 메시지 1건당 읽음 비중

|---|---|---|

| 10:10 | 87.1% | 85.2% |
| 20:0 | 93.1% | 92.0% |
| (나) 2:2(4명 방) | 57.4% | 53.5% |

- A3 예측(읽음 ≈ 90%): **비중 가설은 맞다** — 보는 사람이 많은 방(10명 이상)에서 85~93%. 4명 방에서도 절반 이상
- **방 하나 규모의 병목 가설은 아니다** — 방 하나(20명)는 20:0 r=10까지 앱 4코어 중 ~10%였다. 서버를 포화시킨 것은 방 100개의 합(메시지 ≈ 1,070 + 보고 ≈ 2,070건/초)이고, 그때 첫 병목은 읽음 전용 자원이 아니라 **앱 CPU 전체**였다

## 결론
- 이 환경(앱 2대 × 2코어)의 기준선 한계: **메시지 ≈ 820건/초(앱 CPU 80%)**, 그 위에서 메시지 경로(인바운드 실행기)가 먼저 무너진다. 4,000세션 자체는 문제없다(메모리·연결)
- **운영 첫 병목 = nginx 기본 설정**: 앱은 4,000세션을 받았지만 운영 nginx는 동시 웹소켓 ≈ 768에서 막힌다(운영 확인 값, 측정 환경은 올려 둠)
- 개선 후보(기록만): 읽음 비용 줄이기(디바운스·묶음·보는 사람에게만 — 비중 85~93%), 인바운드 실행기 크기·대기열 상한(포화 때 메시지 우선), Hikari 풀(CPU 다음 한계선), OSIV 끄기(A6), nginx 연결 설정, `-Xmx` 명시
