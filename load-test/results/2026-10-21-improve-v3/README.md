  - (1) 여러 방을 메시지 하나에 담아 한 채널로 발행: 받는 쪽 형식과 구독 구조가 바뀐다. 구독하지 않은 방의 데이터도 모든 서버가 받는다
  - (2) Lua 스크립트로 서버에서 여러 PUBLISH: 파이프라인과 효과가 비슷한데, 스크립트를 따로 관리해야 한다
  - (3) 발행을 다른 스레드·비동기로: 처리 스레드는 빨리 끝나지만, 주기 사이 순서와 실패 처리(다시 담기와 무관한 발행 실패 집계)가 복잡해진다. 지난 결정(E)에서도 비동기는 쓰지 않았다
  - (4) 스냅샷을 DB 대신 메모리에서 만들기: 다른 서버가 갱신한 위치를 모른다. 정확성이 깨진다
- **그대로 둔 것:** 잠금 순서(방·사용자 순 FOR UPDATE), 실패 시 다시 담기, 종료 시 처리, 현재 멤버만 갱신, 갱신과 스냅샷의 트랜잭션 구분
- **발행 실패 처리:** 묶음이 실패하면 그 주기 READ 전부를 실패로 센다(`chat.redis.publish.failed`). 읽음 위치는 이미 저장됐고, 다음 스냅샷이 복구한다(전과 같은 원칙)
- **테스트:** 전체 219/219
  - 새 테스트 `readAllMatchesPerRoom`: 한 문장 결과가 방마다 읽은 것과 같다. 멤버 없는 방도 나오고, version이 같다
  - 새 테스트 `pipelinedPublishReachesEveryRoom`: Redis 방 채널마다 READ가 하나씩 나간다

**측정의 한계(공통)**

- 디스크 동기화 1.9ms와 체크포인트 중 커밋 지연은 측정 장비(WSL2 위 ext4) 값이다. 운영 디스크는 확인하지 않았다
- W=0은 1,200까지, W=500은 4,200까지만 생성기 보정 범위 안이다. 활발한 방 0.9 × 2,400(작업 6 600방)은 생성기 포화로 무효다
- 운영 기본값은 정하지 않았다. 코드 기본값은 모두 꺼 둔 상태다(스레드 0 = CPU × 2, 발행 반납 뒤 끔, 모으기 끔)
